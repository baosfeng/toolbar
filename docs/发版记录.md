### 1.24.0 / 1.24.1 / 1.24.2 为什么跳过

这三版的 `Package.swift` 里 `NetworkMonitorUI` 没有声明 `NetworkMonitorCore` 依赖，
而 `SettingsSkeletonLogic.swift` 等文件 `import NetworkMonitorCore`。干净副本构建直接失败：

```
error: no such module 'NetworkMonitorCore'
```

本机增量构建因为 `.build` 里已有该模块产物而偶然通过，CI 三次连续失败也都是这个错。
依赖直到 `185aebf` 才补上，晚于这三个版本对应的提交——**给它们打 tag 只会得到一个构建失败的 Release**。

这三版的内容没有丢：它们完整包含在 v1.26.0 里（release notes 已注明区间跨越）。

### 1.25.0 为什么也跳过

同一类问题：`AppCoordinator.swift:71` 的 `var notificationService: any NotificationServicing!`
在本机 Swift 6.4 能编，CI 的 macos-26 镜像（Swift 6.3）直接报：

```
error: optional 'any' type must be written '(any NotificationServicing)?'
error: using '!' is not allowed here
```

`d977683` 把它改成 `(any NotificationServicing)!` 才修好（实测干净 worktree 构建 exit=0）。

**教训**：本机能编 ≠ CI 能编。工具链差一个小版本就会让「隐式解包 + 存在类型」这种写法翻车，
而 CI 红三次没人看。发版前必须先确认 CI 绿。

## 发版流程

1. 改版本号：`NetworkMonitor/Scripts/build-app.sh` 内联 Info.plist 的
   `CFBundleShortVersionString` 与 `CFBundleVersion`（构建号必须递增），
   以及根目录 `AGENTS.md` 的「版本」行——这是仅有的两处真源。
2. 提交并推 `github` 远端。
3. 打 tag：`git tag vX.Y.Z && git push github vX.Y.Z`。
4. Release workflow 自动跑：矩阵构建 arm64 + x86_64 → 各自 `lipo` 自证架构 →
   打 zip（`Yilan-<arch>.app.zip`）→ 生成逐条 release notes → 建 release。
5. 用 `ghops actions list baosfeng/toolbar` 跟到底，确认两个 arch 的 run 都 success。

### tag 与版本号不一致会怎样

`setup-build` 这个 composite action 会校验「tag 去掉 v」与 `build-app.sh` 里的
`CFBundleShortVersionString` 完全相等，不等就直接 exit 1。这条是为了防「发 v1.20.0
但包内还是旧版本」的静默错版。

## 签名现状

**当前所有 release 都是 ad-hoc 签名**（`Signature=adhoc`），因为仓库没有配置
`BUILD_CERTIFICATE_BASE64` / `P12_PASSWORD` / `KEYCHAIN_PASSWORD` 三个 secret，
`setup-build` 会跳过证书导入，`build-app.sh` 回落到 ad-hoc。

后果与绕法：

- 用户下载后首次打开会被 Gatekeeper 拦（「无法验证开发者」）；
  右键 →「打开」，或 `xattr -dr com.apple.quarantine /Applications/一览.app`。
- 包内没有公证，不能用 `spctl` 通过。要做成「双击即开」需要 Apple Developer 账号
  （$99/年）+ 证书导出 + notarytool 公证，属独立一轮工作。

本机开发用的是自签证书 `NetworkMonitor Local Signing`（2026-10-18 至 2036-10-15），
它只在有证书的本机生效，不会进 CI。

## 下一步（自动化）

现在发版靠人记着「改两处版本号 + 打 tag」。可以做的：
- `Scripts/release.sh`：读当前版本、校验工作区干净、bump 两处版本号、提交、打 tag、推、
  轮询 workflow 到终态并按结果 exit；
- 或用 GitHub Actions 的 `workflow_dispatch` 输入版本号让 workflow 自己 bump ——
  但那样版本号提交来自 CI，需要额外的分支保护考量。
