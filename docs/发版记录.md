### 1.24.0 / 1.24.1 / 1.24.2 为什么跳过

这三版的 `Package.swift` 里 `NetworkMonitorUI` 没有声明 `NetworkMonitorCore` 依赖，
而 `SettingsSkeletonLogic.swift` 等文件 `import NetworkMonitorCore`。干净副本构建直接失败：

```
error: no such module 'NetworkMonitorCore'
```

本机增量构建因为 `.build` 里已有该模块产物而偶然通过，CI 三次连续失败也都是这个错。
依赖直到 `185aebf` 才补上，晚于这三个版本对应的提交——**给它们打 tag 只会得到一个构建失败的 Release**。

这三版的内容没有丢：它们完整包含在 v1.26.0 里（release notes 已注明区间跨越）。

### 1.26.0 为什么也跳过

`GlassStyle.swift` 里的 `glass.effectIsInteractive` 只在 **macOS 27 的 SDK** 里声明，
CI 的 `macos-26` 镜像 SDK 没有这个符号：

```
error: value of type 'NSGlassEffectView' has no member 'effectIsInteractive'
```

关键在于 `#available(macOS 27.0, *)` 挡的是**运行时**版本，挡不住**编译期缺符号**——
本机 Xcode 26.6 能编，CI 直接红。`5fed4f0` 改成 KVC（先 `responds(to:)` 探 setter，
再 `setValue(_:forKey:)`）才修好。

这是第二次栽在「本机能编 ≠ CI 能编」上（上一次是 `any P!`）。**发版前必须先看 CI 绿。**

### 1.25.0 为什么也跳过

同一类问题：`AppCoordinator.swift:71` 的 `var notificationService: any NotificationServicing!`
在本机 Swift 6.4 能编，CI 的 macos-26 镜像（Swift 6.3）直接报：

```
error: optional 'any' type must be written '(any NotificationServicing)?'
error: using '!' is not allowed here
```

`d977683` 把它改成 `(any NotificationServicing)!` 才修好（实测干净 worktree 构建 exit=0）。

**教训**：本机能编 ≠ CI 能编。工具链差一个小版本就会让「隐式解包 + 存在类型」这种写法翻车，
而 CI 红三次没人看。发版前必须先确认 CI 绿。

## 发版流程

### 一条命令（推荐）

```bash
cd NetworkMonitor
Scripts/release.sh 1.28.0              # 真发版
Scripts/release.sh 1.28.0 --dry-run    # 只做检查，不改任何文件
```

脚本按顺序拦这几件事，任何一步不过就停：

1. 工作区干净、在 `main` 上
2. 新版本号大于当前（逐段按数值比，不会把 `1.9` 判成大于 `1.10`）、本地与远端都还没有该 tag
3. 两条门禁 + `swift build` + `TestRunner`（必须打「所有测试通过」）
4. **CI 闸门**：本地 HEAD 必须已推到远端，且该提交的 check-runs 无 failure、无 in_progress
   —— 1.24.x / 1.25.0 / 1.26.0 五个版本全栽在「本机能编、CI 编不过」，这条就是为它们加的
5. bump 版本号（唯一真源 `NetworkMonitor/version.env` 的 `VERSION` + `BUILD`，同步 `AGENTS.md` 版本行）
   → 提交 → 推 → 打 tag → 轮询 Release run 到终态
6. 发布成功后核对三个资产齐全：`Yilan-<版本>.dmg` / `SHA256SUMS.txt` / `update.json`
   （缺一个都算失败：少了 `update.json`，本次发布的自动更新通道就是断的）

### 手工流程（脚本不可用时）

1. 改 `NetworkMonitor/version.env` 的 `VERSION` 与 `BUILD`（构建号必须递增），
   以及根目录 `AGENTS.md` 的「版本」行——代码真源只有 version.env 一处，AGENTS.md 是派生台账。
2. 提交并推 `github` 远端。
3. 打 tag：`git tag vX.Y.Z && git push github vX.Y.Z`。
4. Release workflow 自动跑：`package` 矩阵两台 runner 各出单架构包 → `universal` job
   合并 + 重新签名 + 打 `Yilan-<版本>.dmg` + 挂载自证 + 算校验和 → `publish` job
   生成逐条 release notes、生成 `update.json`、建 release。
5. 用 `ghops actions list baosfeng/toolbar` 跟到底，确认 package / universal / publish 三段都 success。

### 升级通道的跨越点（1.30.0）

1.29 及更早的更新器只认 `Yilan-<arch>.app.zip` 这种资产名；1.30.0 起发布里只有 universal dmg
（不再有 zip）。因此：

- **1.29 用户**：点「下载并安装」会报「发布里没有安装包」——请让他们在发布页手动下载 dmg
  装一次。装好 1.30.0 之后的版本都能走静态清单 + dmg 自动更新。
- **1.30.0 及以后**：清单通道（`update.json`）优先，回退 API 时也能识别 dmg，
  两条通道都能装上干净包名的「一览.app」。

这条跨越点只在 1.30.0 这一次存在；之后可以删掉这段说明。

### tag 与版本号不一致会怎样

`setup-build` 这个 composite action 会校验「tag 去掉 v」与 `version.env` 的 `VERSION`
完全相等，不等就直接 exit 1。这条是为了防「发 v1.30.0 但包内还是旧版本」的静默错版。

## 签名现状

**当前所有 release 都是 ad-hoc 签名**（`Signature=adhoc`），因为仓库没有配置
`BUILD_CERTIFICATE_BASE64` / `P12_PASSWORD` / `KEYCHAIN_PASSWORD` 三个 secret，
`setup-build` 会跳过证书导入，`build-app.sh` 回落到 ad-hoc。

后果与绕法：

- 用户下载后首次打开会被 Gatekeeper 拦（「无法验证开发者」）；
  右键 →「打开」，或 `xattr -dr com.apple.quarantine /Applications/一览.app`。
- 包内没有公证，不能用 `spctl` 通过。要做成「双击即开」需要 Apple Developer 账号
  （$99/年）+ 证书导出 + notarytool 公证，属独立一轮工作。

本机开发用的是自签证书 `NetworkMonitor Local Signing`（2026-10-18 至 2036-10-15），
它只在有证书的本机生效，不会进 CI。

**对「应用内更新」的影响（1.30.0 起）**：关于页提供「下载并安装」，替换 .app 后
cdhash 变化，TCC 授权（屏幕录制 / 辅助功能 / 输入监控）与登录项需要重新授权。
这条代价在界面上固定显示（`UpdateInstallText.reauthorizationNotice`），
自动安装默认关闭（`update.autoInstall` 缺键即关）。
换成 Developer ID 签名 + 公证后，这个代价会降到「首次打开不再被拦」，
但 TCC 是否保留仍取决于签名身份是否稳定——升级签名方案时需重新评估这段文案。

## 下一步（自动化）

现在发版靠人记着「改两处版本号 + 打 tag」。可以做的：
- `Scripts/release.sh`：读当前版本、校验工作区干净、bump 两处版本号、提交、打 tag、推、
  轮询 workflow 到终态并按结果 exit；
- 或用 GitHub Actions 的 `workflow_dispatch` 输入版本号让 workflow 自己 bump ——
  但那样版本号提交来自 CI，需要额外的分支保护考量。
