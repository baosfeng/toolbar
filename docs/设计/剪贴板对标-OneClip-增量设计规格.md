## 1. 目标与范围

需求：参考 [One-Clip/OneClip](https://github.com/One-Clip/OneClip) 的开源剪贴板核心，优化本项目的剪贴板历史。

范围：**只做 3 项增量**，均不动数据库 schema、不动面板与卡片版式骨架。对标证据逐条带 `文件:行号`，统一收在[调研结论](../调研/剪贴板对标-OneClip-调研结论.md)，本文只写设计与验收。

## 2. 我们已领先的项（本次保持现状）

OneClip 开源核心逐项对比后，以下能力的现状**已经更好**，本次保持现状（证据见[调研结论](../调研/剪贴板对标-OneClip-调研结论.md)第 1 节）：

| 能力 | 本项目 | OneClip | 结论 |
|---|---|---|---|
| 隐私过滤 | Concealed / Transient / AutoGenerated / 自激标记 / bundleID 黑名单，五级优先（`ClipboardContentHasher.swift:56-67`） | 无（全库 grep 0 命中） | 保持现状 |
| 去重键 | SHA256（文本按 CRLF 归一 + 去空白；图片按所选表示原始字节）（`ClipboardContentHasher.swift:97-151`） | Swift `hashValue`，进程随机种子跨会话不稳定 | 保持现状 |
| 存储 | SQLite + 唯一索引 `content_hash` + 排序索引 + `user_version` 幂等迁移（`DatabaseManager+ClipboardSchema.swift:19-52`） | 按日期分目录 `items.json`，每次全量读改写，无 schema 版本 | 保持现状 |
| 重复处置 | 单条原子 upsert：保留原 id、`copy_count+1`、刷新 `created_at` 置顶（`DatabaseManager+ClipboardRepository.swift:30-38`） | 时间窗丢弃 + 删旧插头 | 保持现状 |
| Paste Stack | 有（⌘S 入栈 / ⌘⇧S 清空 / 监听 ⌘V 推进）（`PasteStackController.swift:103-158`） | 无（`showQuickPasteSelector` 只有定义无调用） | 保持现状 |
| 面板不抢焦点 | `.nonactivatingPanel` + `.statusBar` level + `canBecomeKey`（`ClipboardPanelController.swift:41-42, 60-82`） | 普通 `NSWindow` `.normal`，抢焦点 | 保持现状 |
| 搜索 | SQLite LIKE 预筛 + 内存分档打分（1000 / 800 / 600−offset / 300−gaps） | 分词 AND 子串，无打分，`searchItems` 为死代码 | 保持现状 |

## 3. 三项增量

三项缺口清晰、成本可控、用户可感知；按优先级依次为 A（P0 修债务）、B（P1 对标最值得学的机制）、C（P2 识别度）。

### 3.1 增量 A：剪贴板图片磁盘回收（P0，修债务）

**问题（可复现）**：`ClipboardImageStore` 只有写入路径，**无任何删除路径**（`ClipboardImageStore.swift:16-101` 全部是 `store` / `writeThumbnail`）；而 `deleteClipboardItem` / `clearClipboardItems(keepingPinned:)` / `pruneClipboardItems` 只删 DB 行（`DatabaseManager+ClipboardRepository.swift:182-301`）。结果：`~/Library/Application Support/macMonitor/clipboard/images/` 只增不减，删条目 / 清空 / 过期清理都不回收原图与缩略图。

**设计**：

1. 仓储删除类接口改为**返回被删条目**，让上层拿到 `imagePath` 与 `contentHash` 后再删文件：
   - `deleteClipboardItem(id:) -> ClipboardItem?`（原 `Bool` 改为返回被删条目，nil = 不存在）
   - `clearClipboardItems(keepingPinned:) -> [ClipboardItem]`（原 `Int` 改为返回被删条目列表）
   - `pruneClipboardItems(maxItems:retentionDays:) -> [ClipboardItem]`（同上）
   - 协议 `ClipboardRepository` 与全部 mock 同步更新。
2. `ClipboardImageStore` 新增删除能力：
   - `remove(originalPath: String?, contentHash: String, logger:)`：按 `contentHash` 前缀删除 `<hash>.<任意扩展名>`（覆盖落盘时同哈希换扩展名遗留的旧副本，见 `ClipboardImageStore.swift:81-82` 的保留理由——该理由只在「记录仍存在」时成立），并删除 `<hash>_thumb.png`；同时删除 DB 里的 `imagePath` 精确路径（防扩展名不一致漏删）。
   - `sweepOrphans(knownPaths:thumbnailHashes:logger:)`：目录内文件名 stem 不属于已知集合的一律删除。
3. 接线：组合根（`AppCoordinator`）的三处删除调用后，把返回条目交给统一入口 `ClipboardImageGC.reclaim(items:logger:)`；启动完成后延迟 5s 跑一次 `sweepOrphans`（已知集合 = 全量 DB `image_path` + 全部 `content_hash`）。
4. 失败语义：DB 删除先成功，再删文件；删文件失败只 `logger.warning`，不阻断、不回滚 DB。
5. 资源护栏：孤儿清扫固定在启动后跑一次，轮询路径不做目录扫描。
6. 文件切分以实现为准：`ClipboardImageGC` 与 `sweepOrphans` 的落点可由实现方按单文件上限自行拆分，契约仍是本节的方法语义与验收断言。

### 3.2 增量 B：采集器动态轮询 + 剪贴板变更通知（P1）

**对标依据**：OneClip 用 `DistributedNotificationCenter("com.apple.pasteboard.changed")` 做主要触发 + 按用户活跃度动态切换 0.6s / 2.0s / 5.0s 的 Timer，活动判定见 `UserActivityMonitor.swift`；本项目目前固定 500ms（`PasteboardWatcher.swift:16-17, 51-59`）。

**设计**：

1. Core 新增纯函数 `ClipboardPollSchedule`（无 AppKit 依赖，可测）：
   - 入参 `idleSeconds: TimeInterval`、`isAppActive: Bool`；出参间隔。
   - 档位：`idleSeconds < 30 && isAppActive` → 0.5s；`idleSeconds < 300` → 2.0s；否则 → 5.0s。
   - 归一化：负数 / NaN / 无穷 → 按 0 处理（走最快档）。
2. App 层新增 `UserActivityMonitor`：只读 `CGEventSource.secondsSinceLastEventType(.combinedSessionState, .null)`（**免权限**的公开 API，不需要「输入监控」授权），外加 `NSWorkspace` 应用激活通知。**不新增权限申请、不记录按键内容**。
3. `PasteboardWatcher`：Timer 改为「每次 tick 重新计算间隔」的一次性链式 Timer（`pollInterval` 常量保留为活跃档上限，供测试与既有断言使用）；`captureNow()` 与通知唤醒逻辑不变。
4. `DistributedNotificationCenter` 只作**提前唤醒**：收到 `com.apple.pasteboard.changed` 立即跑一次 `capture()`，不改轮询节奏；changeCount 判定仍是唯一准入闸门（不影响现有忽略策略与时序）。
5. 停止语义不变：`stop()` 之后不再有任何 tick 与通知监听；停止时移除通知观察者。

### 3.3 增量 C：文件条目类型细分（P2，识别度）

**对标依据**：OneClip 有 9 类内容类型枚举（`ClipboardItem.swift:3-13`）与独立文件分类器（`ClipboardManager.swift:720-740`）；本项目的 `file` 条目只有一条「文件」图标，多文件混排时看不出是什么。

**设计**：

1. Core 新增纯函数 `ClipboardFileClassifier`：入参路径数组 → `ClipboardFileCategory`（`image / video / audio / document / code / archive / executable / other`）。
2. 分类依据：**扩展名白名单**（显式列举，不做黑名单推断），全部小写比较；空扩展名 → `.other`；多文件时取**各文件分类一致**的类别，混合时返回 `.other`（避免一张卡片上的图标撒谎）。
3. 展示：`ClipboardFileCategory` 提供 `label`（中文，如「图片文件」）与 `symbolName`（SF Symbols，与现有卡片图标同族）。
4. 卡片：落在现有 `ClipboardCardView+Resources.swift` 按分类选图标；数据库 schema、过滤段与卡片尺寸保持现状。
5. 无障碍：图标与分类标签作为卡片 `accessibilityLabel` 的组成部分，保证可读名包含分类。

## 4. 明确不做（登记 backlog，不属本次范围）

| 项 | 理由 |
|---|---|
| 多选 + 批量粘贴 / 批量删除 | 动面板选中态骨架（`selectedIndex` 单值 + 卡片单选中），风险与收益不匹配本次窗口 |
| 富文本 / HTML / 颜色 / 自定义格式完整保留 + Paste as 子菜单 | 需扩展 `ClipboardItemKind`、加 BLOB / 多表示存储、改写回与迁移，属骨架级改动 |
| OCR 可搜索 | OneClip 声称有但源码**无可实现**（全库零 Vision 引用）；[剪贴板历史设计规格](剪贴板历史-设计规格.md)第 13 节已明确不做 |
| Snippets 片段库 / 关键字自动扩展 | 需新表 + 匹配层；`isPinned` 可作过渡 |
| 多端同步（iCloud / 局域网） | 需独立同步层与冲突合并；局域网互传模块可复用传输层，属长期项 |
| 复制次数展示与「常用」排序 | 已有 `copy_count`，排序口径需先定，单独排期 |
| 搜索命中高亮 | 需改卡片绘制与富文本分段，排在多选之后 |

## 5. 验收标准（派发前冻结）

每条都是「命令 + 期望输出」，自述不算证据。

**门禁**

| 组 | 命令 | 期望 |
|---|---|---|
| G-1 | `swift run --disable-sandbox --build-system native TestRunner` | 末行「🎉 所有测试通过！」 |
| G-2 | `bash NetworkMonitor/Scripts/check-file-size.sh`（仓库根） | exit 0，输出「✅ 大文件门禁通过」 |
| G-3 | `swift build -c release --disable-sandbox --build-system native` | exit 0（防 DEBUG 块泄漏） |
| G-4 | `swift build --disable-sandbox --build-system native` | exit 0 |

**行为断言（TestRunner 手写断言，新增用例）**

- A 组（图片回收）：删除单条图片 → 原图与缩略图文件均不存在；清空（保留收藏）→ 收藏图片文件保留、其余删除；超限清理 → 被清理图片文件删除；孤儿清扫 → 目录内无对应记录的文件被删、有记录的文件保留；已知集合为空且目录为空时不报错。
- B 组（轮询调度）：`ClipboardPollSchedule` 三档边界（29.9s / 30s / 299.9s / 300s）、应用非活跃时落慢档、负值 / NaN 归一化到最快档；`PasteboardWatcher` 停止后不再 tick。
- C 组（文件分类）：单文件各类扩展名命中（每类 ≥2 个样本）；无扩展名 → `other`；多文件同类别 → 该类别；多文件混合类别 → `other`；大小写与前后空白归一；空数组 → nil。

覆盖度随结论一起报（新增断言条数）。

## 6. 工程化要求

- 纯函数优先：新增判定逻辑下沉 `NetworkMonitorCore`，AppKit 依赖只留 App 层。
- 可观测：删除与清扫失败走 `LoggingService`（warning 级），路径优先经 `LogRedaction` 脱敏后再落日志（见踩坑「OSLog 的 public 字段全本机可读」）。
- 容错：文件系统调用一律 `do/catch`，失败不抛给 UI。
- 单文件 ≤ 500 行 / 15360 字节；单函数 ≤ 70 行。
- 范围固定为：`ClipboardItemKind`、数据库 schema、面板与卡片尺寸三处保持不变。
