# 提交规范

> ⚠️ **何时阅读：** 当你需要提交代码到 Git 仓库时，必须先阅读本文档，了解提交信息格式和提交策略。

## 提交信息格式

```
<type>: <中文描述>
```

## 允许的 type

| Type | 使用场景 |
|------|---------|
| `feat` | 新增文档或功能模块 |
| `fix` | 修正文档错误或过时内容 |
| `docs` | 纯文档更新（非功能变更） |
| `refactor` | 重构文档结构或组织方式 |
| `test` | 添加或更新文档中的测试示例 |
| `chore` | 构建、配置等杂项变更 |

## 示例

```
docs: 添加网络速度监控模块文档

feat: 新增菜单栏实时网速显示功能

fix: 修正网速格式化计算错误
```

## 开发流程要求

> 所有功能开发必须遵循以下流程顺序，违反此顺序的提交应被拒绝。

```
① 先写文档 → ② 再写代码 → ③ 最后运行测试用例验证
```

- **文档先行：** 任何功能开发前，必须先编写设计文档或接口说明，确认设计后再编码
- **代码验证：** 编码完成后必须运行测试用例，确保功能正确
- **禁止先写代码再补文档：** 文档与代码冲突时，以代码为准，但应当先有文档再写代码
- **提交前必须确保所有测试通过**

## 提交策略

- 代码修改完成后，**一次性提交**完整的代码 + 测试 + 文档变更
- 确保提交后的仓库处于可构建状态
- 每次提交应只包含一个功能变更（按功能单次提交）

> **计划和任务类临时文档不得提交：** 所有规划和任务类临时文档为临时文件，任务完成后会被自动删除，**不得**纳入 git 跟踪或提交。

## 提交确认流程

> 提交代码前必须通过 `ask` 工具经用户确认，**禁止** AI 擅自执行 `git commit` 或 `git push`，**禁止**用自然语言提问代替 `ask` 工具。

### 执行步骤

1. **展示变更清单** — 使用表格列出所有修改/新增/删除的文件
2. **调用 `ask` 工具** — 使用 `ask` 工具的 `questions` 参数构造选择题询问用户
3. **等待 `ask` 工具返回结果** — 根据用户选择的选项执行
4. **执行操作** — 按用户选择的选项执行

### 会话级授权豁免

> 同一会话内，用户通过 `ask` 确认过一次提交后，后续再次提交自动获得授权，无需重复 ask。

### 禁止行为
- ❌ 不得用自然语言提问代替 `ask` 工具
- ❌ 不得擅自决定提交
- ❌ 不得在用户沉默时默认同意
- ❌ 不得以"流程要求自动提交"为由跳过 `ask` 确认

## ✅ 操作前自查清单

在提交代码到 Git 前，请逐项确认：
- [ ] 提交信息格式符合 `<type>: <中文描述>` 规范
- [ ] type 使用了正确的分类（feat/fix/docs/style/refactor/test）
- [ ] 本次提交只包含一个功能变更（按功能单次提交）
- [ ] 所有测试已通过
