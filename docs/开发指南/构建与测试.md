# 构建与测试

> **何时阅读：** 构建项目、运行测试或打包 .app 前。

## 命令

```bash
cd NetworkMonitor

# 编译
swift build --disable-sandbox --build-system native

# 测试（须显示「🎉 所有测试通过！」）
swift run --disable-sandbox --build-system native TestRunner

# 打包部署（自动杀旧进程、复制到 /Applications、启动）
./Scripts/build-app.sh          # debug 模式
./Scripts/build-app.sh release  # release 模式

# 只出包不部署 / 指定架构（发版与交叉构建走这条）
SKIP_INSTALL=1 ./Scripts/build-app.sh release              # 产物 dist/一览.app
ARCH=arm64  SKIP_INSTALL=1 ./Scripts/build-app.sh release  # 产物 dist/一览-arm64.app
ARCH=x86_64 SKIP_INSTALL=1 ./Scripts/build-app.sh release  # 产物 dist/一览-x86_64.app

# 大文件门禁（在仓库根运行；单文件超 500 行 / 15360 字节即失败）
(cd .. && bash NetworkMonitor/Scripts/check-file-size.sh)

# 同族合计门禁（按类名前缀聚合；防「拆成一堆恰好不超限的文件」绕过上面那条）
(cd .. && bash NetworkMonitor/Scripts/check-file-families.sh)
(cd .. && bash NetworkMonitor/Scripts/check-file-families.sh --report)  # 只打印各族合计

# 发布说明生成器回归（Release 正文的「完整变更」链接、逐条 commit 链接、@提及中和）
(cd .. && bash NetworkMonitor/Scripts/test-release-notes.sh)
```

发布说明回归跑的是真实 git 历史（自动取最近两个 v* tag 的区间），只读、不改文件，CI 与
`Scripts/release.sh` 都会先过它——它守的是三件「发出去才发现」的事：compare 链接不能落到
origin 的 codeup owner（GitHub 上是 404）、每条提交的短 hash 要能点进该提交、提交标题里的
`@Sendable` 这类写法不能裸着进正文（GitHub 会当成用户提及，在 Release 页脚挂出假贡献者）。

## 本机环境注意（无 Xcode 时）

**本机当前只安装了 Command Line Tools，没有 Xcode.app**，默认的 swiftbuild/XCBuild 后端在 session 初始化阶段就会失败：

```
SessionFailedError(... "Unknown error parsing property list")
```

**因此本机执行上面命令时，需要统一追加 `--build-system native`：**

```bash
swift build --disable-sandbox --build-system native
swift build -c release --disable-sandbox --build-system native
swift run --disable-sandbox --build-system native TestRunner
```

- 该故障与 `--disable-sandbox` 无关：带与不带都失败；本机只有 CLT 时默认后端必然初始化失败。
- 不是项目配置或代码问题：在干净 git 基线上同样复现。遇到时不要当成代码回归去回滚改动。
- 产物路径不变，仍是 `.build/<arch>-apple-macosx/{debug,release}/NetworkMonitor`（`<arch>` 由 `ARCH` 决定、缺省为本机架构）；`Scripts/build-app.sh` 按同一口径取二进制。

## 双架构发版

发版由 GitHub Actions 完成，**不需要在本机交叉编译**：

- `.github/workflows/release.yml` 用矩阵跑两个 runner：`macos-26`（arm64）与 `macos-26-intel`（x86_64），
  两边都用 `ARCH=<arch> SKIP_INSTALL=1 ./Scripts/build-app.sh release` 出包，
  各自 `lipo -info` 自证架构后再上传 artifact，最后由 `publish` job 一次性建 release。
- 两个架构各自建 release 会撞 422（同一个 tag 只能有一个 release），因此拆成 package + publish 两个 job。
- `.github/workflows/ci.yml` 也用同一份矩阵跑测试：x86_64 只有在 Intel runner 上才真的被编译过，
  只跑 arm64 的话「x86 能不能编过」要到发版当天才知道。
- runner 标签：Intel 侧只有 `macos-26-intel`（`macos-13` 已于 2025-12 下线，`macos-14` 于 2026-11 退役）。
- 发版步骤：改版本号（`build-app.sh` 的 `CFBundleShortVersionString` + `AGENTS.md`）→ 提交 → 推 main →
  `git tag vX.Y.Z && git push github vX.Y.Z` → Release 工作流自动出两个包的 release。
- tag 与 plist 版本不一致时工作流会直接红（`Version matches tag` 步骤），避免发出去的包「关于」里写着旧版本。
- `native` 引擎已被官方标记 deprecated，构建时会多一条 deprecation 警告，可忽略。
- 根治办法：安装 Xcode.app 后执行 `sudo xcode-select -s /Applications/Xcode.app/Contents/Developer`，或重装/升级 Command Line Tools；之后即可去掉 `--build-system native`。
- 详见 [swift build 会话初始化失败](../踩坑/构建/swift-build-会话初始化失败.md)。

Swift 与 Xcode 的配对关系另有一处独立佐证：swift.org 的
[releases.json](https://www.swift.org/api/v1/install/releases.json) 逐条记录每个 Swift 版本对应的 Xcode
（6.3.3 → Xcode 26.6，6.4.0 → Xcode 27.0，6.4.2 / 6.4.3 → Xcode 27.2）。

**结论：CI 与发版实际跑 Swift 6.3.3，本机是 6.4。** 包清单保持 `swift-tools-version: 6.3`，暂不抬到 6.4。

### 为什么不是 `xcode-27`（唯一默认带 6.4 的镜像）

1. **只有 arm64**：`xcode-27` / `xcode-27-xlarge` 都没有 Intel 变体，CI 与发版的 `x86_64` 那一行无处可跑。
   只切 arm64 会让矩阵分裂成「arm64 跑 6.4、x86_64 跑 6.3」两套工具链，等于把
   「x86 能不能编过」这个唯一真判据废掉。
2. **仍是 preview**：见 [runner-images issue #14404](https://github.com/actions/runner-images/issues/14404)，
   preview 不在 Actions SLA 内，容量还在平衡期；而两个 job 分别有 30 / 40 分钟 timeout，排队一抖就红。
3. **基础 OS 换成了 macOS 27**（默认 Xcode 27.1 的 SDK 是 macOS 27），发版路径要在新 SDK 上重验。
4. **Swift 6.4 改了 SwiftPM 默认后端**：[Swift 6.4 Released](https://www.swift.org/blog/swift-6.4-released/)
   写明 Swift Build 成为 SwiftPM 默认。本项目 CI 显式带 `--build-system native`、发版又依赖
   `build-app.sh` 里 `BUILD_SYSTEM=default` 的现有行为——不先验这两条路径就切换，等于静默换了构建引擎。

### 为什么也不是「workflow 里装工具链」

Swift.org 的 macOS 工具链按 Xcode 配对发布（见上面的 releases.json），而 `macos-26` 镜像最高只有
Xcode 26.6：装 6.4 工具链就是编译器与 SDK 跨版本混搭，官方不按这个组合发布。Xcode 27 本身只能从
Apple 开发者账号下 .xip，CI 里没有凭据。所以这条路当前不成立。

### 规则

- CI 与发版只能跑 6.3，**6.4-only 语法禁止进主分支**（例：SE-0521 的 `some Rocket?` / `any P?`
  省括号、SE-0522 的 `@diagnose`）。**本机 pre-commit 全绿 ≠ CI 绿**。
- `.github/actions/setup-build` 的 `Show toolchain` 会打印 `swift --version` / `xcodebuild -version` /
  镜像名，并与 `minimum-swift-version`（默认 `6.4`）逐段数值比对，**低于下限只打 `::warning::` 不失败**。
  这是有意的：今天没有任何 GA 镜像带 6.4，做成 fail 会让每次 CI 与发版立刻变红，而红着的 CI 拦不住任何东西。
  想看「这次到底用什么编的」就看这一步的日志。

### 将来切到 6.4 的判据与清单

判据（满足任一即来改）：runner-images 出现 **GA 的 macOS 27 镜像且有 Intel 变体**，或
`macos-26` 系镜像的默认 Xcode 升到 27.x。

切换时按顺序验四件事：

1. `Show toolchain` 不再告警（`swift --version` ≥ 6.4）；
2. `swift build --disable-sandbox --build-system native` 仍可用——不再可用时先定后端策略，再谈抬工具链；
3. `build-app.sh` 的 `BUILD_SYSTEM=default` 在 6.4 下变成 Swift Build，发版产物要重验架构自证
   （`lipo -info`）与真能启动；
4. 编译告警基线仍为 0 条（判据见 AGENTS.md「构建与发布」）。

## 测试约定

- 测试目标 `TestRunner`（手写断言，本机无 Xcode SDK，不用 XCTest）
- 新增测试：新建 `Sources/TestRunner/<域>Tests.swift`，用 `assertEqual` / `assertNotNil` 写断言，
  再到 `Sources/TestRunner/TestSuites+<域>.swift`（Core / Clipboard / Snip / Billing / Token / Pane / System / Transfer）
  加一行调用。**`main.swift` 不再改**（只剩 40 行：人工探针入口 + 8 个域函数调用 + `TestAssertions.finish()`，
  不再随测试增长，500 行门禁不再是约束）
- 断言失败**累计**：`assertEqual` 等不再首错即停，套件跑完由 `TestAssertions.finish()` 统一打汇总并 `exit(1)`，
  一次运行能看到全部 ❌。`guard … else { exit(1) }` 这类「后续断言没意义」的前置条件失败仍然即停
- 退出码语义不变：全绿 `exit(0)` 且打印「🎉 所有测试通过！」，有失败 `exit(1)`
- 忘了登记的测试套件由 `runTestSuiteRegistrationTests` 判红（扫源码判「定义了却没有任何调用」），不会被静默跳过
- 登记位置就是域函数（`TestSuites+<域>.swift`），**不是 `main.swift` 加一行**——main.swift 只调 8 个域函数
- 数据库测试用 `db.initializeInMemory()`（内存 SQLite，无需真实文件）
- 测试覆盖：Core 工具函数、DatabaseManager（建表/迁移/upsert）、剪贴板仓储与搜索、额度 provider、互传协议与传输、货币时区配置

## 产物

- 可分发包在 `dist/一览.app`（已 .gitignore），部署目标 `/Applications/一览.app`
- 包名由 `build-app.sh` 的 `APP_BUNDLE_NAME`（=「一览」）决定；**包内可执行名**由 `APP_EXECUTABLE_NAME`
  （=「一览」，与 `CFBundleExecutable` 同源）决定，所以二进制路径是 `一览.app/Contents/MacOS/一览`。
  构建产物仍是 `.build/<triple>/<config>/NetworkMonitor`（SwiftPM target / 模块名不变，打包时复制改名）
- 部署到新包名时会顺手删掉旧包 `/Applications/NetworkMonitor.app`（先杀掉从旧路径启动的实例）；
  杀进程判据同时扫现有可执行名与 `LEGACY_EXECUTABLE_NAMES`（历史英文名 NetworkMonitor），
  避免改名当天「没找到进程」→ `rm -rf` 正在运行的包
- 运行：`open /Applications/一览.app` 或 `swift run`

## 提交前流程（每次代码修改后）

```
① 大文件门禁 bash NetworkMonitor/Scripts/check-file-size.sh（在仓库根运行）
①' 同族合计门禁 bash NetworkMonitor/Scripts/check-file-families.sh（在仓库根运行）
② 编译 swift build --disable-sandbox --build-system native
③ 测试 swift run --disable-sandbox --build-system native TestRunner
④ 打包 ./Scripts/build-app.sh（如需）
⑤ 提交（信息见提交规范）
```

> 提交前必须运行测试，修复所有失败用例。

### 大文件门禁 hook（可选安装）

把门禁挂到 pre-commit，提交时自动拦截超限文件（无需每次手动跑）：

```bash
# 在仓库根执行一次
git config core.hooksPath NetworkMonitor/Scripts/git-hooks
```

- 路径推荐用相对仓库根，换机器 / 换 clone 后仍直接生效。
- 关闭（恢复 git 默认钩子目录）：`git config --unset core.hooksPath`
- 临时跳过（不建议）：`git commit --no-verify`
- 门禁只读检查，不改文件；阈值可用 `CHECK_MAX_LINES` / `CHECK_MAX_BYTES` 覆盖。
