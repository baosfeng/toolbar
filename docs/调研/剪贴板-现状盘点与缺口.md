## 二、数据分析：数据库是否需要改、迁移机制怎么走

### 2.1 表定义与字段

`clipboard_items` 唯一定义在 `NetworkMonitor/Sources/NetworkMonitorCore/DatabaseManager+ClipboardSchema.swift:19-36`：

```
id TEXT PK / kind TEXT / text TEXT / preview TEXT / image_path TEXT
image_width INT / image_height INT / content_hash TEXT / source_bundle_id TEXT
source_app_name TEXT / copy_count INT / is_pinned INT / created_at REAL
pinned_at REAL / stack_position INT
```
索引两条：`idx_clipboard_content_hash`（UNIQUE，`:37`）、`idx_clipboard_order`（`is_pinned DESC, created_at DESC`，`:38`）。

### 2.2 迁移机制（这是最大的结构性约束）

- `migrateClipboardSchema()` 是**幂等建表 + 一次性置版本**：先无条件跑 `CREATE TABLE IF NOT EXISTS` 与两条 `CREATE INDEX IF NOT EXISTS`（`:17-45`），再 `guard clipUserVersion(db) < 2 else { return }`，最后 `PRAGMA user_version = 2`（`:47-53`）。
- 调用链：`DatabaseManager.migrateIfNeeded()`（`DatabaseManager.swift:158-165`）→ `migrateClipboardSchema()`，在 `initialize()`（`:114`）与 `initializeInMemory()`（`:149`）各跑一次。
- **没有版本阶梯骨架**：不存在 `if version < 3 { ... }` 的增量段，也不存在 `ALTER TABLE` 用法（全库 grep `ALTER TABLE` 零命中）。加列/加表必须自己新写分支并提升版本号。
- **两处硬编码位置耦合**，加列必须同时改：
  1. `ClipboardSchema.columns` 列串（`DatabaseManager+ClipboardSchema.swift:62-65`）；
  2. `clipItem(from:)` 的下标映射（同文件 `:116-138`，`clipText(stmt, 0)` … `clipIntOrNil(stmt, 14)`）。
  只改一处会静默错位读（不报错、数据串列）。
- **测试锁死版本号**：`TestRunner/ClipboardRepositoryTests.swift:39` 断言 `user_version == 2`、`:45` 断言重复迁移仍为 2。任何版本提升都会让这两条失败，必须同步改断言（这是「有既有测试锁住这块行为」的直接证据）。

## 四、缺口逐条详述

### 缺口 1｜Pinboard 多分组收藏（缺失）

- 现状：收藏 = 布尔置顶。`isPinned` 同时承担「星标」与「豁免清空/超限」两种语义（`ClipboardItem.swift:21-22,46-47`）；写入口唯一 `setClipboardItemPinned`（`ClipboardRepository.swift:58-61`），实现写两列 `is_pinned` + `pinned_at`（`DatabaseManager+ClipboardRepository.swift:150-174`）。
- 数据：需新表 + 外键列，user_version 2→3。
- UI：过滤控件现在四段定宽 40（`ClipboardPanelView+Subviews.swift:44`），放不下「分组」；建议把 `NSSegmentedControl` 换成下拉或「全部/文本/图片/收藏」+ 独立分组条。
- 测试锁：`setClipboardItemPinned` 有 6 条断言（`ClipboardRepositoryTests.swift:86,92,96,99,103`、`ClipboardSearchLimitsTests.swift:85,111`），改语义会大面积变红。
- 量级：8–10 文件 / +500–800 行（含迁移测试）。

### 缺口 2｜条目就地编辑（缺失）

- 现状：仓储无 update；卡片是整卡自绘，卡内零子视图（`ClipboardCardView.swift:7-18` 注释明示「卡内没有任何子视图」）。
- 难点：就地编辑必须在自绘卡上叠一个 `NSTextView`（`ClipboardCardView` 有 `acceptsFirstResponder = false`，`:133`），或改为「详情区编辑」——后者风险低得多（详情区本来就是 `NSTextField` + 滚动，`ClipboardDetailStripView.swift:20-29`）。
- 必须先定口径：编辑后 `content_hash` 怎么办（重算＝可与别条合并冲突；置空＝破坏唯一索引约束，因 `idx_clipboard_content_hash` 是 UNIQUE 且 `content_hash NOT NULL`）。这是**语义风险高于实现成本**的一项。
- 量级：3–4 文件 / +150–250 行。

### 缺口 3｜新建条目（缺失）

- 现状：只有采集路径（`PasteboardWatcher.capture()` → `onCapture` → 组合根落库，`AppCoordinator+Clipboard.swift:51,82-92`）。
- 可复用：`saveClipboardItem` 就是 upsert（`DatabaseManager+ClipboardRepository.swift:29-37`），手写一条只需自造 content_hash。
- 量级：4–6 文件 / +200–350 行（依赖缺口 2 的编辑控件，两者应同批做）。

### 缺口 4｜Quick Look 空格预览（缺失）

- 现状：零引用。键盘拦截表（`ClipboardPanelController+Keyboard.swift:23-51`）没有空格分支——当前空格在搜索框输入态是正常字符，所以**必须在 `hasQuery` 时让位**（现有 ⌫ 已有这套让位逻辑，`:27` 可照抄）。
- 实现：`QLPreviewPanel` + `QLPreviewItem` 数据源；图片条目给原图 URL（`item.imagePath`），文本条目给临时 .txt（或用 `QLPreviewPanel` 的自定义视图）。面板是 `.nonactivatingPanel`（`ClipboardPanelController.swift:59-60`），QL 面板层级与其共存需实测。
- 量级：2–3 文件 / +120–200 行。

### 缺口 5｜多选与批量操作（缺失）——**改动面最大的一项**

- 现状：`selectedIndex: Int` 穿透 5 个文件：`ClipboardPanelController.swift:42`、`ClipboardPanelView.swift:128`、`ClipboardCardFlowView.swift:56`、`ClipboardCardView.swift:105`、`ClipboardDetailStripView` 的选中输入。
- 卡片交互当前不读修饰键：`ClipboardCardView+Interaction.swift:32-39` 只看 `clickCount`，`ClipboardCardHitTest.action` 甚至显式丢弃 region（`ClipboardCardGeometry.swift:162-170`，`_ = region` 在 `:165`）。
- 仓储侧无批量接口；批量删除必须走 `clipDeleteBatch` 才能拿到被删条目做图片回收（否则会漏删图片文件，形成孤儿——现有孤儿清扫只在启动后跑一次，`ClipboardImageGC.swift:73-89`）。
- 设计文档已明确登记为「本次不做」：`docs/设计/剪贴板对标-OneClip-增量设计规格.md:82`「动面板选中态骨架（`selectedIndex` 单值 + 卡片单选中），风险与收益不匹配」。
- 量级：8–12 文件 / +500–900 行。

### 缺口 7｜OCR（缺失，底座现成）

- 现成资产：`VisionTextRecognizer`（`Snip/VisionTextRecognizer.swift:14-60`，accurate 档 + 中英自动检测 + 置信度）、Core 纯函数整理（`SnipTextRecognition.swift:30-59`，排序/过滤/拼接，测试在 `TestRunner/SnipTextRecognitionTests.swift`）、像素守卫解码 `ClipboardImageDecoder.guardedCGImage(fromFileAt:)`（`ClipboardImageDecoder.swift:158`）。
- 缺的三块：① 落库列 + 搜索并入；② 采集完成后的后台识别调度（图片条目目前只有缩略图后台管线 `ClipboardThumbnailLoader`，可作为节流/去重范式）；③ 结果展示（详情区）与「复制识别文字」动作。
- 隐私：OCR 全本地（Vision），不涉网，符合项目「数据仅存本机」。
- 设计文档已登记不做（`docs/设计/剪贴板对标-OneClip-增量设计规格.md:84`，理由是 OneClip 声称有但源码零实现）——**这是对标结论，不是技术障碍**；本仓库反而有可复用的真实现。
- 量级：6–8 文件 / +500–800 行。

### 缺口 8｜来源 App / 日期范围筛选（缺失）

- 现状：过滤档位写死在枚举里，且分两处用（视图 `matches` 与控制器 `applyFilter`）。`ClipboardPanelSearch.match` 已经接受 `filter: ClipboardFilter`（`ClipboardPanelSupport.swift:17-26`），扩参即可。
- 数据齐备：`source_bundle_id` / `source_app_name` / `created_at` 都有，且 `fetchAllClipboardItems` 拿的是全量（`ClipboardPanelController.swift:195`），内存过滤零成本。
- UI：工具条 160pt 放不下「来源 + 日期」两个维度；且 `ClipboardFilter` 是 `Int` rawValue 且用 `selectedSegment` 直连（`ClipboardPanelView.swift:206`），改成多维筛选要重做控件（建议分段保留 + 一个「筛选」弹层）。
- 量级：5–7 文件 / +300–500 行。

### 缺口 9｜暂停采集（缺失）

- 现状：只有「采集模式」（`ClipboardCaptureMode`），没有「临时暂停」。`PasteboardWatcher.stop()`（`PasteboardWatcher.swift:76-88`）幂等、状态回调 `.stopped`（`:86`），语义上可直接复用为暂停。
- 接入点：① 偏好键（`ClipboardPreferences.swift:53-67` 加一键）；② `GlobalHotKeyCenter` **只能注册 1 个热键**（固定 id `hotKeyIdentifier = 1`，`GlobalHotKey.swift:128,131`）——暂停快捷键要么改造热键中心支持多注册，要么挂在面板内键位（如 `⌘P`）；③ 面板页脚/菜单栏需要可见状态（`ClipboardPanelView.swift:193-201` 的 `showHint` 通道可复用）。
- 量级：4–5 文件 / +120–200 行；若走独立全局热键，热键中心改造另算 +100 行。

### 缺口 10｜类型识别（部分）

- 现状：只在「显示」时猜。`ClipboardItemKindLabel.label` 只认 `http(s)://` 前缀（`ClipboardItemKindLabel.swift:13-17`）；卡片图标另写一份猜测（`ClipboardCardView+Resources.swift:10-17`，多认 `www.`、JSON、命令）——**两份口径已经不同步**，是现存的隐性缺陷。
- 若只做展示层：抽一个 Core 纯函数 `ClipboardTextClassifier`（URL / email / color / json / command），两处调用点收敛，不需 DB 改动，+80–150 行、2 文件，且能立刻消掉口径分歧。
- 若做独立 `kind`：要在 4 个 switch 落点全改（`ClipboardItemKindLabel.swift:18-23`、`ClipboardCardView+Resources.swift:6-18`、`ClipboardPaster.swift:53-64`、面板 `ClipboardFilter.matches`），且旧 `text` 数据不迁移则「筛选文本」会漏掉新类型的旧条目。
- 颜色识别还缺采集侧：当前 RTF 只取纯文本（`PasteboardWatcher.swift:254-265`），`cocoa.pasteboard.color` 类型完全没读。
- 量级：展示层 2 文件 +80–150 行；独立类型 5–7 文件 +300–450 行。

### 缺口 11｜拖拽到其他 App（缺失）

- 现状：零拖拽源。同仓库现成范式在局域网互传：`TransferRows.swift:80`（`NSDraggingSource`）、`:177-189`（`NSDraggingItem(pasteboardWriter:)` + `beginDraggingSession` + `draggingSession(_:sourceOperationMaskFor:)`）。
- 实现：`ClipboardCardView` 加 `mouseDragged`（阈值 3-5pt 后再起拖，否则会和单击选中抢事件——当前 `mouseDown` 直接 `onClick`，`ClipboardCardView+Interaction.swift:32-39`）；`NSPasteboardItem` 按 kind 构造：图片走多表示（可复用 `PasteboardWriter.imagePasteboardItem`，但那是 private，需放宽或抽公共）、文件写 `.fileURL`、文本写 `.string`。
- 量级：2–4 文件 / +150–250 行。

### 缺口 13｜搜索高亮（缺失）

- 现状：`ClipboardFuzzySearch` 有分数但不返回命中区间（`ClipboardFuzzySearch.swift:49-58` 只返回排序后的条目），无法直接高亮；且卡片正文由 `DrawnTextBlock` 单色绘制（`ClipboardCardView+Content.swift:66-72`），不支持分段着色。
- 要做需两步：① 打分侧返回 `[Range<String.Index>]`（注意 `ClipboardCardTextStyle.breakable` 会插入零宽空格，`:42-67`，区间映射会被打乱）；② `DrawnTextBlock` 支持 attributed 分段或叠加底色矩形。
- 量级：3–4 文件 / +200–350 行。

### 已有能力的关键边界（避免低估）

- **Paste Stack**：依赖辅助功能权限（`PasteStackController.swift:82-85` 无权限拒绝入栈），且**不能拦截目标 App 原生 ⌘V**，只能「监听 ⌘V 后把队首写回剪贴板让原生粘贴读到」（`:104-117`）。这意味着：用户按住 ⌘V 已被 `isARepeat` 过滤（`:183-184`），但**任何** ⌘V（包括用户想粘贴别的内容）都会推进栈——这是设计取舍，不是 bug。
- **⌘1–9**：作用于 `filteredItems` 的当前顺序（`ClipboardPanelController+Keyboard.swift:80-84`），即搜索/过滤后的前 9 条，不是全局前 9 条。
- **图片 GC**：条数上限与保留天数只清「非收藏」（`DatabaseManager+ClipboardRepository.swift:254,262`），收藏条目无限累积——没有「收藏也占额度」的口径，也没有总量的硬上限。

## 五、基础设施判断

### 5.1 数据模型扩展成本：**低-中（列级低，表级中）**

- 加**列**便宜：建表语句就在一个文件里，加列改 2 处（`columns` 串 + `clipItem` 下标）+ 1 段 ALTER 分支；测试只需改 2 条版本断言。
- 加**表**（Pinboard / OCR 旁表）也不难，但**版本阶梯要先补**：当前 `migrateClipboardSchema` 是「一次性 v2」，没有任何 `switch version` 骨架（`DatabaseManager+ClipboardSchema.swift:47-53`）。第二个迁移必须自己写 `if clipUserVersion(db) < 3`，且**要保证 `PRAGMA user_version = 2` 那行不再无条件执行**——现有代码是 `guard < 2 else return` 之后写 2，照抄这个模式会写不出 v3 段。这是必须改结构的地方。
- **真正的成本在「位置耦合」**：`ClipboardSchema.columns`（列串）与 `clipItem(from:)`（`:116-138` 的 0…14 硬下标）必须同步改，且 `clipItem` 对非法 kind 直接返回 nil（`:119`）——**未识别的 kind 值会静默丢行**，因此「扩展 `ClipboardItemKind`」这类改动有数据不可见风险，必须先定「旧值兼容读」策略。
- 仓储协议 12 个方法是一个文件里的单一协议（`ClipboardRepository.swift:27-91`），加方法要同步改 `TestRunner/ClipboardPanelTests.swift:12-76` 的 `MockClipboardRepository`——好消息是只有这一个 mock，坏消息是它 64 行必须整体跟着长。

### 5.2 UI 骨架能否承载新交互：**部分能，两处是硬墙**

能承载的：
- 右键菜单有成熟的四段式分发（构造 / 枚举 / 响应链 / 执行），加「编辑」「新建」「OCR 复制」是低风险增量。
- 详情区是常驻的 `NSTextField` + 滚动容器，是「编辑」「OCR 文本」「来源/时间」最省事的承载面。
- 设置页已有六块卡片 + 一个 delegate 协议，加开关类设置是模板化工作。

硬墙一：**工具条是 4 槽定宽纯函数**。`toolbarMetrics`（`ClipboardPanelLayout.swift:118-133`）把 search / filter / capture / help 四个矩形算死，参数只有 `width` 与 `captureWidth`；640pt 下 search 已停在下限 300、filter 定宽 160，再加控件只能压缩搜索框或换行。且这套算术被断言锁住（`ClipboardDetailStripTests.swift:153-181`，含 `:175` 窄面板 480pt 下搜索框停在下限、`:178` 过滤定宽 160 不压缩）。任何「往工具条加东西」的需求都要先动这个纯函数 + 断言，不是加个按钮就行。

硬墙二：**卡片流是单行横向、卡片是整卡自绘**。多选需要「点 + ⌘/⇧ 累加选中」，但选中态当前是单 `Int` 且卡片零子视图（`ClipboardCardView.swift:7-18,105`）；就地编辑需要在自绘卡上叠 `NSTextView`，而卡片 `acceptsFirstResponder = false`（`:133`）、点击即选中（`ClipboardCardView+Interaction.swift:32-39`）。拖拽需要区分「单击」与「拖动」，也和当前「mouseDown 直接 onClick」冲突。**这三项（多选 / 就地编辑 / 拖拽）都指向同一个改造：把卡片的命中-动作模型从「mouseDown 即动作」升级为「press-drag-release 状态机」**，这是本模块唯一的结构性重构点。

### 5.3 门禁约束（会直接卡住实现）

- `Scripts/file-family-baseline.txt` 是**棘轮**，只允许变小。当前剪贴板相关族：`Clipboard/ClipboardPanelController 606`、`Clipboard/ClipboardPanelView 522`、`Clipboard/ClipboardCardView 836`、`Clipboard/ClipboardCardFlowView 407`、`Clipboard/PasteboardWatcher 367`、`Settings/SettingsClipboardPane 586`（`check-file-families.sh --report` 实测）。
- 含义：**任何在现有族里加功能的实现都会撞门禁**（controller 与 cardView 两族几乎无余量）。新能力必须新开文件（如 `ClipboardPanelController+Selection.swift`、`ClipboardCardView+Drag.swift`），并且族名规则是「文件名第一段（遇 + 或 . 截断）」（`check-file-families.sh:51-58`）——所以新文件**必须挂在已有族前缀下**才不会另开一个新族（另开新族本身不违规，只是语义上更该复用既有族）。
- 单文件 500 行 / 15360 字节门禁现为全绿（766 文件），`ClipboardCardView.swift` 321 行、`ClipboardPanelController.swift` 282 行尚有空间，但族合计没有。
