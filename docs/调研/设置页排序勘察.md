# 设置页排序勘察：现有分类/行结构，与「设置项自定义排序」的落点

> **何时阅读：** 要给设置窗口加「自定义排序」（行顺序 / 卡片顺序 / 侧栏分类顺序），或判断某个设置项该不该允许排序时。
>
> 勘察范围：`NetworkMonitor/Sources/NetworkMonitor/Settings/`（26 个文件，3874 行）+ Core 里的偏好存储 + 菜单栏渲染端。只读勘察，未改动任何源码。

## 一、结论摘要

| 项 | 结论 |
|---|---|
| 设置行总数 | **99 行固定行**（7 个分类、34 张卡片）+ 动态行（「忽略的应用」列表 N 行） |
| 已支持排序 | **10 行**（面板分页 6 行、工具条组顺序 4 行），且都是「独立顺序卡 + 上移/下移链接按钮」，无拖拽 |
| 不支持排序 | **89 行**；其中真正值得排序的核心是**菜单栏指标 20 行**——它不仅决定设置页行序，还直接决定菜单栏上屏顺序 |
| 真正的缺口 | 菜单栏指标只有「显示集合」偏好，**没有任何顺序偏好**；渲染端 `makeStatusParts` 用 15 条硬编码 `if` 链写死顺序，20 个指标里有 **5 个从未上屏** |
| 推荐机制 | 卡片内「上移/下移 + 恢复默认」为主，顺序存**逗号分隔的 String rawValue 列表**；设置行顺序只依赖「切页即重建」生效，菜单栏指标顺序额外走既有 `AppEvents.menuBarDisplayChanged` 热生效 |
| 迁移关键 | 默认顺序**必须显式写死**当前渲染顺序，不能用 `MenuBarMetric.allCases` 兜底——两者顺序不同，直接兜底会让老用户升级后菜单栏外观立刻变化 |

## 二、现状：七分类怎么定义

> 勘误：本文是排序改造前的勘察快照（当时七分类）；1.24.0 已扩到九分类（新增「外观」「通知与音效」），排序三处的键与机制未变。

- 分类枚举：`SettingsSection: CaseIterable`，7 个 case 顺序即侧栏顺序（`SettingsSection.swift:8-15`）；`title` / `symbolName` / `fileSuffix` / `subtitle` 四组 switch 全在同一 enum（`:18-67`）。注释明写「顺序即展示顺序」。
- 侧栏渲染：`SettingsWindow.makeContentView()` 遍历 `SettingsSection.allCases` 建 `SettingsSidebarItemView`（`SettingsWindow.swift:78-84`），点击走 `select(section)`。
- 内容区**切页即重建**：`select()` 每次都调 `factories[section]?()` 新建 pane，旧 pane 直接 removeFromSuperview（`SettingsWindow.swift:132-137`）。因此「设置页自身的行顺序」改完重新进页就生效，**不需要发事件**。
- 页基类 `SettingsPaneView`（`SettingsPaneView.swift:11-38`）持有 `page: SettingsPageStack`；子类只在 `buildContent()`（init 时调一次）里往 `page` 加卡片，`refresh()` 在切页 / 窗口重新显示时同步状态。

### 5.1 渲染端铁证：菜单栏顺序硬编码

`MenuBarManager+StatusTitle.swift:33-51` 是 15 条顺序 `if` 链，顺序固定为：
↓ 下载 → ↑ 上传 → CPU → GPU → MEM → 压力 → Disk → R/W → WiFi → BAT → Temp → Today → Token → HIT → 7d。

而 `MenuBarMetric.allCases`（`MenuBarDisplayPreferences.swift:7-15`）声明顺序为：
`up, down, peakUp, peakDown, todayTraffic, weekTraffic, cpu, gpu, memory, memoryPressure, diskFree, diskIO, thermal, wifi, battery, load, tokenToday, tokenCacheHit, tokenWeek, billingRemaining`。

**两处顺序不同**：up/down 相反；wifi/thermal 前后相反；todayTraffic 在 allCases 第 5 位、渲染却第 12 位。

**且 20 个指标里有 5 个从未上屏**：`peakUp`、`peakDown`、`weekTraffic`、`load`、`billingRemaining`（`makeStatusParts` 无对应分支）。设置页却给它们画了开关——这 5 个当前是**死开关**。做排序前必须先决定「补齐上屏」还是「标注本版不参与菜单栏」。

### 5.2 另外两处硬编码顺序（同属本次范围）

- 菜单栏两行布局按「指标数均分」切上下行：`MenuBarDisplayLogic.statusTitle`（`NetworkMonitorUI/MenuBarDisplayLogic.swift:104-111`）——指标顺序改了，双行排版自动跟着改，无需另写逻辑。
- `menuBarMetricToggled` 用 `toggle.tag = metric.hashValue`（`SettingsGeneralPane.swift:94`）再遍历字典反查（`:181-187`）。`hashValue` 不保证稳定、字典遍历顺序随机——排序改造时应一并改成「tag = 数组索引」或闭包捕获。

## 六、方案：「设置项自定义排序」

### 6.1 推荐机制（一段话）

**卡片内行级排序为主、卡片间排序为辅、侧栏分类排序最后做。** 每个「可排序作用域」定义一个稳定 id（一律 **String rawValue**，不用 Int），偏好里存**逗号分隔的 id 列表**；读取时统一过「去未知 / 去重 / 缺失按默认顺序补尾」的纯函数，缺键直接回落代码默认顺序且**不写回**。UI 侧新增 `SettingsOrderedCardView` 容器（内部生成行 + 行尾「上移/下移」`SettingsLinkButton` + 行副标题「第 N 项」），把现在散在两处的重复代码收敛；卡片标题右侧放「恢复默认」链接按钮。**v1 不做拖拽**：现有两处已建立的交互就是按钮，拖拽要引入 NSDragging 会话 + 自动滚动，收益低且与「设置页无拖拽先例」冲突（仓库唯一拖动在 `Transfer/TransferRows.swift:172-191`，语义是文件拖出）。

热生效分两条：
- **设置页自身的行顺序**：不需要事件。`SettingsWindow.select()` 每次重建 pane（`SettingsWindow.swift:132`），写偏好后重新进页即生效；若要「当场看到行移动」，在 pane 内整卡重建（`NSStackView` 挪单行会让 `SettingsCardView.addRow` 的分隔线重复）。
- **菜单栏指标顺序**：必须发既有 `AppEvents.postMenuBarDisplayChanged()`；`MenuBarManager+DisplayPreferences.swift:14-22` 已订阅并立刻 `update()` 重渲染。

### 6.2 落点：不改 `SettingsSection`，每个作用域自己维护 order

不建议在 `SettingsSection` 上加 `orderable`——分类是**窗口层**概念（`SettingsWindow` 的侧栏），「设置项排序」是**页内层**概念；混在一处会让每个 pane 都被迫知道分类的可排序性。推荐三层各自独立：

| 层 | 数据结构 | 键 | 归属 |
|---|---|---|---|
| 侧栏分类 | `[SettingsSection]` | `settings.order.sidebar` | `SettingsWindow` 读，`SettingsSection` 提供 `orderKey` |
| 卡片顺序 | `[String]`（卡片 id） | `settings.order.<pane>.cards` | 各 pane 的 `buildContent()` |
| 卡片内行 | `[String]`（行 id，通常是枚举 rawValue） | `settings.order.<pane>.<card>` | `SettingsOrderedCardView` 的调用方 |

### 6.3 偏好存储格式

```swift
// Core: NetworkMonitorCore/Infrastructure/SettingsOrderPreferences.swift
public enum SettingsOrderKey {
    public static let sidebar = "settings.order.sidebar"
    public static let menuBarMetrics = "settings.order.menuBar.metrics"
    // 卡片 / 行作用域按需追加
}

/// 顺序列表编解码 —— 与 SnipToolBarListCoding 同源口径
public enum SettingsOrderCoding {
    public static func decode(_ raw: String?) -> [String]      // 逗号切分 → 去空白 → 丢空项
    public static func encode(_ ids: [String]) -> String       // join(",")
    /// 去未知、去重、缺失按 all 顺序补尾
    public static func normalize(_ ids: [String], all: [String]) -> [String]
}
```

- **值**：`"downSpeed,upSpeed,cpu,gpu,..."`（String rawValue 逗号串）。
- **理由**：仓库三个既有键（`panel.tabs.order` / `menuBar.metrics` / `snip.toolbar.groupOrder`）全是逗号串，偏好层无 JSON 先例（JSON 只出现在网络协议与 `PairingStore`/`KnownPeerStore` 的列表持久化）。逗号串可直接走 `KeyValueStorage.string(forKey:)`，测试断言是纯字符串比较。
- **若坚持 JSON**：建议只用于「顺序 + 可见性合一」的新作用域，结构 `{"order":["..."],"hidden":["..."]}`；但与既有三键口径分叉，需同时改三处才有收益。**不推荐 v1 引入**。
- **存储实例**：一律构造器注入 `any KeyValueStorage`（默认 `AppContext.shared.storage`），严禁各页自己 `new`——这是 `docs/踩坑/运行时/设置项写了不生效.md` 的第一类故障。

### 6.4 与「面板分页排序」复用同一套组件：可行，但要先补稳定 id

- **存储层可复用**：`PanelTabPreferences` 的 `move/reset/orderedVisibleTabs` 语义与通用层一致，可改成 `SettingsOrderPreferences<MenuPanelTab>` 的薄包装，保留现有 API 名称避免改调用方。
- **必须先解决的坑**：`MenuPanelTab` 是 **Int rawValue**，`panel.tabs.order` 存 `"0,1,2,3,4,5"`（`:39`）。**将来在枚举中间插入新分页，旧 Int 顺序会整体错位**（旧值 3 指向新语义）。通用机制用 String rawValue 正是为绕开这个坑；面板分页要么同步迁到 String 键（`settings.order.panelTabs` + 一次性读旧键迁移），要么明确「面板分页不再插入新 case」。
- **UI 层可复用**：`SettingsOrderedCardView` 落地后，`SettingsGeneralPane.buildPanelTabsCard`（`:200-219`）与 `SettingsCapturePane+ToolBar.buildToolBarCard` 的顺序卡（`+ToolBar.swift:61-74`）都可换成它，同时获得「恢复默认」按钮（当前两处都没有，尽管 `reset()` 早在 `PanelTabPreferences.swift:84-87` 写好）。

### 6.5 迁移与默认值

| 场景 | 处理 |
|---|---|
| 老用户无该键 | 返回代码默认顺序，**不写回**（踩坑文档：读路径缺键只回落、不回写） |
| 默认顺序怎么定 | **显式常量**，不用 `allCases`。菜单栏必须写 `MenuBarMetric.defaultOrder` 精确复刻 `makeStatusParts` 当前顺序，未上屏 5 项追加尾部——否则升级后所有用户菜单栏外观立刻变化 |
| 新增设置项 | `normalize` 补到末尾（复用 `SnipToolBarGroup.order(from:)` 范式），不影响已有顺序 |
| 删除设置项 | `normalize` 丢弃未知 id，不整份丢弃 |
| 非法 / 空串 | 回落默认顺序（与 `panel.tabs.order` 的 `raw.isEmpty` 判据一致） |
| 面板分页 Int→String | 若迁移：读旧 `panel.tabs.order` 的 Int → 映射新 id → 写新键 → 删旧键；一次性、幂等 |

## 七、哪些设置项不该允许排序（白名单思路）

**做法**：不用黑名单「禁止哪些」，而是**显式白名单**列出可排序作用域（与项目既有「识别/触发类逻辑用白名单」一致），未列入的一律不可排序。

**可排序（v1 白名单）**：
1. 通用 › 菜单栏显示 › 指标行（20 行 → 先修完 5 个死开关）
2. 通用 › 面板分页 › 6 行（已有，接通用组件 + 恢复默认）
3. 截图与贴图 › 排列顺序 › 4 组（已有，同上）
4. 剪贴板 › 唤起与面板、采集、操作反馈（10 行纯配置项，v2）
5. 截图与贴图 › 标注、贴图（5 行纯配置项，v2）
6. 侧栏 7 分类（v2，需评估用户是否真想改分类顺序）

**明确不做排序（附理由）**：

| 对象 | 理由 |
|---|---|
| 关于页 4 行（版本/构建号/项目地址/退出） | 语义固定；「退出」被拖到顶部容易误触 |
| 权限 2 行（剪贴板访问 / 辅助功能） | 展示**系统状态**而非配置，顺序变化无意义 |
| 只读派生行（Provider 刷新节奏 3 行、图片占用 / 目录 2 行） | 数值随运行变化，顺序不是用户的选择 |
| 高危动作行（清空图片存储、清理接收目录、退出） | 应**固定在末位**，但破坏性操作优先可恢复 |
| 动态来源行（Provider 3 行、忽略的应用 N 行） | 顺序来自注册表 / 系统 app 列表；要排序须另存 id 顺序，注册表变化会打乱，v1 不做 |
| 单行卡片（启动、额度提醒、数值单位、接收、传输、采样…） | 无可排序对象，控件不该出现 |
| 快捷键 6 行 | 排序无用户可见收益，且行内含录制态（冲突时变红） |
| 常驻工具 chip（10 个） | 已按 `SnipTool.allCases` 分两行摆，属「集合选择」不是顺序；若要做应并入工具条组统一机制 |

**实现约束**：白名单写在调用侧（pane 的 `buildContent` 里只对白名单卡片用 `SettingsOrderedCardView`），不写在 `SettingsSection` 上——这样「新增分类时不会因为忘记配置而默认获得排序」。

## 八、风险与验收

| 风险 | 应对 |
|---|---|
| 排序键用了临时 id | 一律枚举 String rawValue；面板分页 Int 键需迁移或冻结 |
| 老用户外观突变 | 默认顺序显式常量且等于当前渲染顺序（写测试锁死） |
| 死开关 | 排序前先处理 `peakUp/peakDown/weekTraffic/load/billingRemaining` 5 项 |

| 偏好写了不生效 | 菜单栏路径必须发 `menuBarDisplayChanged`；设置页路径靠切页重建 |
| 行重排后分隔线重复 | `SettingsCardView.addRow` 会自动补线（`:158-166`）；行内重排走「整卡重建」，别挪单行 |

**验收口径（建议）**：
1. `swift run --disable-sandbox --build-system native TestRunner` 全绿，含新增顺序断言。
2. 真机：改菜单栏指标顺序 → 上屏顺序同步变化（对照组：不排序时改开关顺序不应变化）。
3. 清空偏好键 → 重新打开设置页 → 行序 = 代码默认顺序。
4. `SettingsWindow+Snapshot.swift` 快照各页：新排序控件可见、行高仍 40pt（注意离屏快照里 `NSSwitch` 不可辨，需文本取证，见 `docs/踩坑/运行时/离屏快照看不出开关状态.md`）。
