# 签名权限失效 / 网络页折线过短 / 贴图拖动变透明 —— 三缺陷调研

> 调研形态：只读侦察，未改任何源码、未 commit、未建分支。
> 证据口径：命令输出逐字摘录 + file:line。凡未跑通的写进「未验证」。
> 采集时间：2026-11-25（本机 macOS 27 / Swift 6.4）。

## 结论摘要

**问题 2（dmg 安装后权限全部失效）**：本应用有**两套签名形态**，一边是本机构建用自签证书（DR = `identifier + certificate leaf`），另一边是 CI / 发布包因未配证书回落 ad-hoc（DR = `cdhash`）。用户把本机证书签名的包换成从 GitHub 下载的 ad-hoc 包，designated requirement 从「证书叶子」变成「cdhash」，TCC 视为**另一个应用**，屏幕录制 / 辅助功能 / 输入监控 / 本地网络 / 登录项全部作废。修法方向：**优先让 CI 也带同一张自签证书签名**（只改 secrets，零代码），立刻消除形态跳变；退路是启动时检出「签名变过」并给一键重新授权引导。

**问题 4（网络页实时折线太短、中间大空白）**：sparkline 宽度被硬编码成 **84pt**，两侧列之间又塞了一个弹性 `spacer()`，把剩余约 96pt 全部吸收成空白。修法方向：折线跟随列宽撑满（最小改动），或改成上下两行各占满整行（推荐）。

**问题 7（拖动贴图越来越透明）**：拖动链路本身**一个 alpha 都没写**（只 `setFrameOrigin`），alpha 的全部写点只有 init / 键盘 / ⌃+滚轮 / 中键重置四处。其中 `PinWindow.scrollWheel` 无条件吞下所有滚动事件（**不过滤 `phase` / `momentumPhase` / 精确滚动**），`⌃` 仍按着时惯性阶段每帧 `adjustAlpha(-0.03·delta)` 累减，很快贴到下限 0.1，体感就是「越拖越透明」。修法方向：滚动入口加「拖动会话中忽略」「惯性 / 触控板放行」两道闸，并把 alpha/scale 换算下沉成可断言的纯函数。

## 逐问题证据

### 问题 2：手动安装 dmg 后系统权限全部失效

#### 现象
用户原话：「然后我手动下载 dmg 进行安装了，然后之前设置的权限，现在需要重新设置，比如屏幕录制等权限，这些就全都过期了，这是为什么？」

#### 代码定位

**签名公共实现**（`build-app.sh` 与 `make-universal-app.sh` 共用一份）：`NetworkMonitor/Scripts/lib-signing.sh`

- `:19` 证书名默认值：`SIGN_IDENTITY="${SIGN_IDENTITY:-NetworkMonitor Local Signing}"`
- `:47-60` 两条签名分支：`--sign "${SIGN_IDENTITY}"`（USE_SIGNING_CERT=1）与 `--sign -`（ad-hoc，`:56`）
- `:69-73` **静默回落点**：

```bash
if security find-identity -v -p codesigning 2>/dev/null | grep -q "${SIGN_IDENTITY}"; then
    USE_SIGNING_CERT=1
else
    USE_SIGNING_CERT=0
fi
```

- `:95-100` **ad-hoc 分支只打警告、不阻断**：

```bash
if [ "$USE_SIGNING_CERT" = "1" ]; then
    echo "      使用证书：${SIGN_IDENTITY}"
    assert_stable_signature "$target"
else
    echo "      ⚠️  未找到证书 ${SIGN_IDENTITY}，回落 ad-hoc（每次构建权限会重新询问）"
fi
```

注意 `assert_stable_signature`（`:24-33`，检查里含「要求文本出现 cdhash 即失败」）**只在有证书时才被调用**——真正需要它的场景（没有证书）恰好绕过了它。

**打包 / 部署链**：

- `build-app.sh:346-348` 单架构：`swift_build` → `package_app`
- `build-app.sh:456` 部署到 /Applications 后**再签一次**：`sign_app_bundle "$INSTALL_PATH"`
- `build-app.sh:360` `SKIP_INSTALL=1` 分支同样 `sign_app_bundle "$APP_DIR"`
- `make-universal-app.sh:133-134` universal 合并后**重签**：`sign_app_bundle "$OUT_APP"`
- `.github/workflows/release.yml:64-71` 证书 secret **可选**：`certificate-base64: ${{ secrets.BUILD_CERTIFICATE_BASE64 }}`；`:90` / `:150` `SIGN_IDENTITY: ${{ secrets.SIGNING_IDENTITY || "NetworkMonitor Local Signing" }}`

**历史沿革（git log 实证）**：
- `abc4597`（2026-10-24）`chore: 签名身份可配置，Release 支持证书签名` —— **第一次**让 CI 可以证书签名，但写成「可选 secret」：`HAS_SIGNING_CERT: ${{ secrets.BUILD_CERTIFICATE_BASE64 != 空 }}`，缺 secret 时整步 `if` 跳过、回落 ad-hoc。
- `10e5272`（2026-11-22）`feat: 发版产物改为 universal dmg` —— 抽出 `lib-signing.sh`，「证书找不到就回落 ad-hoc」这条静默分支随之成形（`:69-73`）。
- 结论：**ad-hoc 是「CI 上没配证书 secret」的直接后果，不是设计选择**；`docs/发版记录.md:129-140` 也自述「因为仓库没有配置 `BUILD_CERTIFICATE_BASE64` / `P12_PASSWORD` / `KEYCHAIN_PASSWORD` 三个 secret，`setup-build` 会跳过证书导入，`build-app.sh` 回落到 ad-hoc」。

三份包的对照一眼看出问题所在：

| 包 | 来源 | 签名 | designated requirement | 能否继承已有 TCC 授权 |
|----|------|------|------------------------|------------------------|
| `/Applications/一览.app`（1.31.0） | 本机 `build-app.sh` 部署 | 证书 | `identifier "com.bsfeng.yilan" and certificate leaf = H"a75da71b..."` | 基准 |

| `Yilan-1.30.0.dmg` | GitHub CI | ad-hoc | `cdhash H"cbbe6839..."` | **不能** |
| `Yilan-1.31.0.dmg` | GitHub CI | ad-hoc | `cdhash H"079f779d..."` | **不能** |

**结论：形态差异来自「本机构建（有证书）vs CI 构建（无证书 secret）」，不是版本差异。** 连 1.30.0 → 1.31.0 两个相邻的 CI 发布之间 DR 都不相同（`cbbe6839...` → `079f779d...`），所以只要继续装 CI 包，**每次升级都要重授权**。

**(c) 两种 DR 互不满足 —— 这就是「权限全部失效」的直接机制**

```text
# 用「本机已装包」的 DR 去校验「下载包」
$ codesign --verify -R="identifier \"com.bsfeng.yilan\" and certificate leaf = H\"a75da71b2ffa5f24c17723206f1d739940b63521\"" "/Volumes/一览 1.31.0/一览.app"

# 用「下载包」的 cdhash DR 去校验「本机已装包」
$ codesign --verify -R="cdhash H\"079f779de52602cf00be5cb5ed0deb38c95c6329\"" /Applications/一览.app
test-requirement: code failed to satisfy specified code requirement(s)

# 各自对自己（本机包 vs 本机 DR）→ 通过，无输出
$ codesign --verify -R="identifier \"com.bsfeng.yilan\" and certificate leaf = H\"a75da71b...\"" /Applications/一览.app
(通过，exit 0)
```

TCC 条目键可理解为 `(service, client=bundle id, csreq)`，其中 csreq 就是 DR；DR 不等价 → 系统判定为不同应用 → 旧授权条目不再命中，界面显示「未授权」，用户必须回系统设置重新勾选（屏幕录制还要重启进程才生效）。

**(d) 「为什么每次重建 cdhash 都会变」—— 实测：cdhash 由内容决定，重签本身不引入随机性**

```text
# 同一二进制 ad-hoc 重签两次：CDHash 不变
$ codesign --force --sign - --identifier com.bsfeng.yilan ./probe_bin && codesign -dv --verbose=4 ./probe_bin | grep CDHash
CDHash=0fe3bf4212867ad0b8e9a838e340e401b34a8634
# 再签一次
CDHash=0fe3bf4212867ad0b8e9a838e340e401b34a8634

# 只改一个字节后重签
$ printf X | dd of=probe_bin bs=1 seek=8000000 count=1 conv=notrunc
$ codesign --force --sign - --identifier com.bsfeng.yilan ./probe_bin && codesign -dv --verbose=4 ./probe_bin | grep CDHash
CDHash=2f4c35ab32730704928f218e55be6b85e641524b

# 同一个包的 ad-hoc DR 形态（注意 # 前缀表示这是隐式指定的要求）
$ codesign -d -r- ./probe_bin
# designated => cdhash H"0fe3bf4212867ad0b8e9a838e340e401b34a8634"
```

即：ad-hoc 的 DR 是**二进制内容的纯函数**，任何一次重建只要字节不同就换身份。

**对照实验：换成证书签名后，DR 不再随内容变化**（同一份二进制复制两份，其中一份改一个字节，都用本机证书签，脚本见「可复跑命令」）：

```text
=== a_bin（证书签）===
CDHash=b79c67fac35b508d569442598441f1753e7ca548
Authority=NetworkMonitor Local Signing
designated => identifier "com.bsfeng.yilan" and certificate leaf = H"a75da71b2ffa5f24c17723206f1d739940b63521"

=== b_bin（证书签，内容差一个字节）===
CDHash=e8695f248fd57bb4ae928f29a46b4cf68992c9df     # 内容变了，cdhash 照样变
Authority=NetworkMonitor Local Signing
designated => identifier "com.bsfeng.yilan" and certificate leaf = H"a75da71b2ffa5f24c17723206f1d739940b63521"   # 但 DR 逐字相同

=== 用 a 的 DR 校验 b ===
PASS: b 满足 a 的 designated requirement

=== 对照：ad-hoc 同场景（c / d 只差一个字节）===
c DR: # designated => cdhash H"0fe3bf4212867ad0b8e9a838e340e401b34a8634"
d DR: # designated => cdhash H"e4031fde8771d085173f3df0e06d970b7eea8b16"
test-requirement: code failed to satisfy specified code requirement(s)     # 不满足
```

**这就是修法候选 a 的可行性证明**：证书签名下 cdhash 仍会变，但 DR 认的是「证书叶子 + bundle id」，内容变化不影响它可以被满足 → **TCC 授权跨版本保留**。ad-hoc 下 DR 认 cdhash，内容一变换身份。

本仓重建必然改字节——

- 每次 `swift build` 重链，Mach-O 里的 UUID / 符号顺序 / 调试信息长度随源码与缓存状态变化（`build-app.sh:84-92` 注释已列「增量与全量的切换条件」：debug↔release、ARCH 切换、BUILD_SYSTEM 切换、build.db 损坏、并行首跑）；
- `build-app.sh:224` 把构建产物 `cp` 成 `Contents/MacOS/一览`；`build-app.sh:238 → :162-191` 每次从本机 Homebrew 重拷 `libzstd.1.dylib` 与 `zstd` 并 `install_name_tool` 改写 id / 依赖；
- `make-universal-app.sh:91-95` `lipo -create` 重新产出 Mach-O；
- 只要内容变 → cdhash 变 → DR 变 → TCC 全部失配。

#### 用两三句人话回答用户

你现在这台机器上装的「一览」是**用本机钥匙串里那张证书签的**，系统记授权时认的是「这张证书」。而 GitHub 上发布的 dmg 因为在 CI 上没配证书，被签成了**匿名（ad-hoc）**，系统记授权时认的是一串跟文件内容绑定的哈希。两者对 macOS 来说是**两个不同的应用**，所以之前勾过的屏幕录制、辅助功能、输入监控、本地网络、登录项全部对不上号，得重新勾一遍。更糟的是 ad-hoc 每重建一次哈希就变一次，所以只要你继续装 CI 打的包，每次升级都要重授权。**根治办法是把那张自签证书也配到 CI 上**，让下载包和你自己打的包签成同一个身份。

#### 现有「系统权限」页对这两件事做了什么

### 问题 7：拖动贴图时透明度越来越低

#### 现象
用户原话：「我移动贴图的时候，贴图的透明度还会发生变化，越来越透明了，这里也有问题」。

#### 代码定位（拖动链路逐段读完）

**内容视图** `NetworkMonitor/Pin/PinContentView.swift`
- `:36` `acceptsFirstMouse` 恒 true；`:44-47` `hitTest` 收敛到本视图
- `:51-63` `mouseDown` → `PinClickIntent.outcome` → `.dragWindow` → `beginDrag()`
- `:77-84` `beginDrag()` 只记起点，**不碰 alpha**：

```swift
guard let window else { return }
dragSession = PinDragSession(startOrigin: window.frame.origin,
                             startMouse: NSEvent.mouseLocation)
```

- `:86-98` `mouseDragged` 只改原点，**不碰 alpha**：

```swift
window.setFrameOrigin(session.origin(forMouse: mouse))
```

- `:100-103` `mouseUp` 只清会话

**拖动会话纯逻辑** `NetworkMonitor/Sources/NetworkMonitorUI/PinDragSession.swift:28-38`：`origin(forMouse:)` 与 `isDragBeyondThreshold`，纯坐标运算。

**窗口** `NetworkMonitor/Pin/PinWindow.swift`：拖动链路上**没有任何 alpha 写入**。

#### 根因分析：alpha 的全部写点只有 4 处，可疑点只在 scrollWheel

```text
$ grep -rn "alphaValue\|adjustAlpha" NetworkMonitor/Sources/NetworkMonitor/Pin/*.swift
PinWindow.swift:74     alphaValue = CGFloat(PinDefaultAlphaResolver.resolve(...))   # 建窗读偏好一次
PinWindow.swift:122    case .alphaDelta(let delta): adjustAlpha(by: delta)          # ⌃+ / ⌃- 键盘
PinWindow.swift:132    adjustAlpha(by: event.scrollingDeltaY * 0.03)                 # ⌃ + 滚轮
PinWindow.swift:174    alphaValue = 1                                                # 中键重置
PinWindow.swift:217-219 func adjustAlpha(by delta: CGFloat) { alphaValue = min(max(alphaValue + delta, 0.1), 1) }
```

**可疑点：`scrollWheel` 无条件吞下所有滚动事件**（`PinWindow.swift:130-137`）

```swift
override func scrollWheel(with event: NSEvent) {
    if event.modifierFlags.contains(.control) {
        adjustAlpha(by: event.scrollingDeltaY * 0.03)
    } else {
        setScale(currentScale * (1 + event.scrollingDeltaY * 0.02), anchor: NSEvent.mouseLocation)
    }
}
```

它**没有**判断 `event.phase` / `event.momentumPhase` / `hasPreciseScrollingDeltas`。对照本仓已有的正确纪律（`NetworkMonitorFeatureSmoothScroll`：带 `phase` / `momentumPhase` 或标了连续滚动的一律原样放行），贴图窗这里是**全吃**，包括触控板双指滚动与**惯性阶段（momentum）**——惯性会持续投递一长串递减的 scroll 事件，`⌃` 若仍按着（不少用户拖移窗口时习惯按住 ⌃ 或 ⌃ 与三指手势叠加），`adjustAlpha` 每帧 `-0.03 × delta` 累加，几帧内就贴到下限 **0.1**，视觉上正是「越拖越透明」。

另一处结构性隐患：`:131` 只判 `.control`，而 macOS 的「⌃ + 滚动」在某些键鼠设置下会被系统转成「缩放 / 显示台前调度」，因此**同一个手势既可能在滚动路径上改 alpha，也可能在拖移窗口时被别的进程消费**——这正是「拖的时候改了 alpha」这种「动作错配」的典型来源。

**这段立即能验，且已验证**（AppKit 离屏复刻 `PinWindow.scrollWheel` 逐字同构 + 真实 `NSEvent(cgEvent:)` 构造事件，脚本 `/tmp/pin_scroll_harness2.swift`）：

```text
== 经内容视图响应链投递 10 次 ⌃ + scroll(deltaY=-6) ==
window.scrollWheel 命中 = 10 / 10          # 内容视图没重写 scrollWheel → nextResponder 直落窗口
alpha 序列 = 0.90 -> 0.72 -> 0.54 -> 0.36 -> 0.18 -> 0.10 -> 0.10 -> 0.10 -> 0.10 -> 0.10
从 0.9 起连续 5 次 deltaY=-6 后 alpha = 0.10
```

两个结论：① 贴着图滚动**一定**会进 `PinWindow.scrollWheel`（内容视图 `PinContentView` 与 `imageView` 都没重写它，事件沿响应链直落窗口）；② 单格 `deltaY=-6` 就是 **-0.18**，从任何常见默认值（0.9 / 1.0）起 **5 格内贴到 0.1**——「越拖越透明」的体感与 5 格完全对得上（触控板惯性阶段一送就是一长串事件）。

`adjustAlpha` 的钳制（`:218`）是 `min(max(alphaValue + delta, 0.1), 1)`，下限 0.1 保证不会彻底消失，但也意味着**一旦被连续滚动打到 0.1，视觉上就接近全透明**。

**次要可疑点**：`PinWindow.swift:66` `isMovableByWindowBackground = true` 与自定义拖动并存（注释说是兜底）。这条不落在 alpha 路径上，但会让「一次拖移」出两种窗口位移来源，干扰复现。

#### 修法建议

1. **最小改动（拦事件）**——`PinWindow.swift:130` 前加两道闸：
   - 拖动会话进行中直接 `return`（由 `PinContentView` 把 `isDragging` 暴露给窗口，或窗口侧记一个 `isDraggingPin`）；
   - 过滤 `event.momentumPhase != []` 与 `event.phase != []`（惯性 / 触控板一律放行，不调 alpha 也不调 scale）。
   改动面：`PinWindow.swift` 约 8 行 + `PinContentView.swift` 约 4 行（`var isDragging: Bool { dragSession != nil }`）。
2. **口径下沉成纯函数**——把「一次滚动 → (newAlpha, newScale)」抽成 `PinScrollAdjustment.adjust(alpha:scale:modifiers:phase:momentumPhase:deltaY:)` 放进 `NetworkMonitorUI`（AppKit 无关，TestRunner 可直接断言），`PinWindow.scrollWheel` 只做「读事件字段 → 调纯函数 → 写回」。改动面：新增 1 文件约 40 行 + `PinWindow.swift` 约 5 行改调用 + 测试约 50 行。
3. **回归测试（必须）**：新增 `PinScrollAdjustmentTests`，断言四条——① 惯性事件（`momentumPhase != []`）不改 alpha 也不改 scale；② 拖动会话中滚动被忽略；③ `⌃` + 负 `deltaY` 时 alpha 单调下降且钳到 0.1、`⌃` + 正 `deltaY` 时回升且钳到 1；④ 无 `⌃` 只改 scale、alpha 恒不变。
