# 系统监控（第二批指标）· 可行性调研

> 目的：第一批已拿下 CPU / GPU 利用率 / 内存 / 磁盘 / 温度（见 [系统监控 CPU/GPU 可行性调研](系统监控-CPU-GPU-可行性调研.md)）。本轮对**第二批候选指标**（GPU 功耗、进程 Top-N、负载、电池、Wi-Fi 链路、P-state 驻留、屏幕状态、风扇、频率、磁盘健康等）做穷举实测，给出可做 / 不可做四档判定与采样预算，供 [系统监控设计规格](../设计/系统监控-设计规格.md) 的下一轮迭代直接取用。
>
> 调研时间 2026-10。结论全部来自**可运行探针的真实输出**，不是文档推断。

## 二、逐项详述

### 2.1 GPU 功耗（IOReport Energy Model）— 本轮最大发现

探针 `probe_ioreport.swift`（含 Metal 负载对照）。`Energy Model` 组共 162 个通道，混了三种单位标签 —— **不是全组统一单位**：

```
units seen: ["uJ", "nJ", "mJ"]
GPU Energy  raw=   290295980  unit=nJ =>  0.2903 W     <- 唯一有值的累加器
CPU Energy  raw=           0  unit=mJ =>  0.0000 W     <- 恒 0
EACC_CPU / PACC0_CPU / PACC1_CPU / DRAM0 / ANE0 / ISP0 / MSR0 / DCS0 / AVE0 / AMCC0 => 全 0
```

同一探针同进程内做 Metal compute 压满对比：

```
--- IDLE 1s:    GPU Energy raw= 290295980 => 0.2903 W
--- LOAD 1s #1: GPU Energy raw=2560500280 => 2.5605 W
--- LOAD 1s #2: GPU Energy raw=2556685210 => 2.5567 W
--- AFTER 1s:   GPU Energy raw= 298086450 => 0.2981 W
```

- **单位必须是 nJ**：raw 值 ÷ 1e9 ÷ 窗口秒数 = 瓦。若把 nJ 当 mJ 会放大 1000 倍（会出现「0.29 kW」这种荒谬读数）；若当 uJ 会放大 1000 倍方向相反。取单位一律读通道自带的 unit 字段，不能硬编码。
- **只有 `GPU Energy` 有值**，CPU 侧全部恒 0（见 §3「整机功耗」），因此**无法用本组数据合成整机功耗**，UI 不出「整机功耗」项。
- **与第一批记录的 ≈3.2 W 不符**：本轮 Metal 压满稳定 2.56 W、空闲 0.29 W，未复现 3.2 W。差异可能来自负载强度（本轮 kernel 只做 20 万次 FMA）或机器温度状态。**UI 必须标注「估算」**，不得当绝对功耗。
- **成本**：Energy Model 全组 162 通道一次读取 1.76 ms。只需要 GPU 一个通道时可只订阅该通道，成本还能再降。
- **三处会 SIGSEGV 的写法与唯一稳定写法见 [IOReport 读取崩溃](../踩坑/运行时/IOReport读取崩溃.md)**，实现前必读。

### 2.2 进程级 Top-N CPU% 与常驻内存

探针 `probe_procs.swift` / `probe_timebase.swift` / `probe_final.swift`。

**时基是这个指标最致命的坑**：`proc_pidinfo(PROC_PIDTASKINFO)` 的 `pti_total_user` / `pti_total_system` 单位是 **mach ticks，不是纳秒**。本机 `mach_timebase_info` = **125/3**，即 **1 tick = 41.6667 ns**。按 ns 直接换算会小 **41.67 倍**：

```
=== mach_timebase_info ===  numer/denom: 125/3   ns per tick: 41.6667
=== 3 线程自旋 0.4 s 实测 ===
  raw delta (pti_total_user+system) = 28612112
  HYPOTHESIS 1: delta is ns          =   7.2%     <- 错！
  HYPOTHESIS 2: delta is mach ticks  = 298.0%     <- 对（期望 ~300%）
```

正确公式与完整反例见 [进程 CPU 百分比的时基换算](../踩坑/运行时/进程CPU百分比时基换算.md)。

**实测 Top-10**（1 s 窗口，708 个进程里 485 个有差分值）：

| 进程 | CPU% | RSS |
|---|---|---|
| Google Chrome for Testing | 34.27% | 239.9 MB |
| Google Chrome for Testing Helpe | 25.41% | 146.4 MB |
| Google Chrome for Testing Helpe | 22.18% | 196.0 MB |
| DeepSeek Harness Helper (Render | 19.14% | 557.1 MB |
| DeepSeek Harness Helper | 17.68% | 61.6 MB |
| qemu-system-aarch64 | 16.35% | 804.0 MB |
| WeChatAppEx Helper (Renderer) | 15.77% | 242.3 MB |
| DeepSeek Harness | 15.20% | 951.0 MB |
| Google Chrome Helper (Aperitif) | 11.33% | 63.8 MB |
| fontd | 10.71% | 7.9 MB |

**开销**：

```
proc_listpids(PROC_ALL_PIDS)   0.0964 ms   (nproc=692, got=673)
proc_pidinfo(PROC_PIDTASKINFO) 0.00704 ms  单进程
全量扫 455 进程               1.310 ms
```

**坑**：

- 必须手写 `_silgen_name` 绑 `libproc` —— `import libproc` 在仅 CLT 环境不可用。
- `proc_taskinfo` 结构体在 Swift 里**不会自动布局**，需自己写（96 字节、18 字段、**Int32/UInt64 混排**）；写错则 `proc_pidinfo` 返回 −1，表现为「所有进程都读不到」而不是崩溃。
- 遍历时跳过 `pid <= 0`；大量进程 `proc_pidinfo` 返回 −1（权限 / 僵尸），本机 708 → 485 有效，属正常现象，不要当错误刷日志。
- CPU% 是差分指标：首帧只有基线，必须像现有 GPU / 磁盘那样**首帧给 nil 而不是 0**。
- 单进程 >100% 是正常的（多线程），实测自旋 3 线程 = 298%，不要 clamp 到 100。
- `proc_pid_rusage` 虽然有更细的磁盘 / 唤醒字段，但**无公开的 `rusage_info_current` 布局**，只能按 `[UInt64]` 数组硬读索引（`ru[2]`、`ru[3]`、`ru[8]`），字段顺序随 macOS 版本变 —— 不上生产。

### 2.3 负载与调度状态

探针 `probe_misc.swift`：

```
=== getloadavg ===  returned: 3   load 1/5/15: 3.578 / 4.563 / 4.606   cost: 0.00675 ms
=== ProcessInfo ===
  thermalState: 0 (nominal)      isLowPowerModeEnabled: false
  processorCount: 10 active=10   physicalMemory: 16 GiB
  systemUptime: 98868.5 s = 27.46 h
  thermalState poll cost: 0.000036 ms
```

- `getloadavg` 0.0068 ms，基本免费，且能补上 CPU% 看不到的「排队压力」语义（负载 > 核数即排队）。P0。
- `ProcessInfo.thermalState` / `isLowPowerModeEnabled` 都是纳秒级，可以直接跟 1 s 周期跑。
- **坑**：`kern.boottime` 是 `timeval` 结构不是 `Int64`，用 `sysctlUInt64` 读会得到 nil；开机时长直接用 `ProcessInfo.systemUptime` 更省事。

### 2.4 电池与电源

探针 `probe_battery.swift`：

```
=== IOPSGetPowerSourceDescription (cost 1.4404 ms) ===
  Current Capacity = 80        Max Capacity = 100      Is Charged = 0
  Is Charging = 0              Is Present = 1          Power Source State = AC Power
  DesignCycleCount = 300       Name = InternalBattery-0    Transport Type = Internal
=== IOPSGetTimeRemainingEstimate ===  seconds: unlimited(-2)   <- AC 接入时的正常返回
=== IOPSCopyExternalPowerAdapterDetails ===
  Name = 96W USB-C Power Adapter   Watts = 94   Current = 4690 mA   AdapterVoltage = 20000 mV
=== AppleSmartBattery (51 props) ===
  CycleCount = 89   DesignCycleCount9C = 1000   MaxCapacity = 100
  Voltage = 12227 (mV)   Amperage = 0   TimeRemaining = 65535 (无效哨兵)   ExternalConnected = 1
```

**坑**：

- `AppleSmartBattery.TimeRemaining` 在 AC 接入时是 **65535 哨兵值**，`Amperage=0` 同理，都要过滤，否则会显示「剩余 18 小时」。
- `IOPSGetTimeRemainingEstimate` 返回 **−2 (unlimited)** 表示 AC 供电，不是错误。
- **电池健康度百分比严格不可得**：51 个 props 里既没有 `BatteryHealth` 也没有 `DesignCapacity`，只有 `CycleCount=89` 与 `DesignCycleCount9C=1000`。UI 只能给「循环次数 89 / 1000」，**不能给健康度百分比曲线**。
- `IOPSGetPowerSourceDescription` 的 `Max Capacity=100` 是**百分比**不是 mAh，别当电池容量。
- 1.44 ms 成本偏高，建议 **5 s 一次**，不必跟 1 s 周期。

### 2.5 Wi-Fi 链路（CoreWLAN）

探针 `probe_wifi.swift`：

```
interfaces: ["en0"]   powerOn: true   serviceActive: true
rssiValue(): -66      noiseMeasurement(): -90        cost: 2.3039 ms
channelNumber: 149    channelBand: 2 (5GHz)          channelWidth: 3 (80MHz)
transmitRate: 144.0   transmitPower: 1496            activePHYMode: 6 (ax)
ssid(): nil <-- Location denied      bssid(): nil <-- Location denied
CLLocationManager.authorizationStatus: 0 (notDetermined)
scanForNetworks: 4 networks (ssid 均为 nil)
```

**坑**：

- `CWInterface.noise()` 在 macOS 27 SDK 已移除，只能用 `noiseMeasurement()`。
- `ssid()` / `bssid()` 返回 **nil 而不是抛错** —— 这是 macOS 11+ 的 Location 门控，不是 bug。**不建议为此申请定位权限**：菜单栏 App 弹定位授权体验极差。
- `scanForNetworks` 能返回 4 个网络的 RSSI（−82 / −60 / −43）但**没有 SSID**，拿不到「周边网络名」。
- 轮询成本 3.24 ms 偏高（`rssiValue()` 本身 2.30 ms），建议 **2–5 s 一次**，别按 1 s 跑。

**VPN / utun**：`getifaddrs` 扫到 `utun0/1/2/3` 存在，成本 <0.01 ms。注意 macOS 默认就会起 utun0/1（不全是 VPN），判定要用「存在 utun 且带非 link-local 地址」，或者只显示一个 VPN 标志位。

### 2.6 风扇转速 — 完全不可得（5 条路径证据）

这是第一批遗留的待办（当时只写了「SMC 键路径不存在」），本轮把 5 条路径全部穷举完毕：

| 路径 | 探针 | 实测结果 |
|---|---|---|
| ① SMC 键 `F0Ac/F0Tg/F0Mn/F0Mx` | `probe_thermal.swift:116-160` | `ioreg` 扫 `"F[0-9]Ac"` 等 → **0 命中**；`AppleSMCKeysEndpoint` props 只有 `IOClass/Generation/role/...` 共 22 键，**无任何风扇键** |
| ② `AppleSMCSensorDispatcher` | `probe_thermal.swift:14-24` | 匹配 1 个实例，props **无风扇值**；子节点只有 `AppleARMPMUPowerSensor`×100 / `AppleARMPMUTempSensor`×62 / `AppleSMCInterface`×2 / `AppleSMCClient`×7 |
| ③ ioreg 全树搜 fan 节点 | `probe_thermal.swift:118-145` | `IOService` plane 扫 **2205** 节点 → fanNodes=**0**；`IODeviceTree` plane 扫 **358** → **0** |
| ④ IOHID 传感器全页穷举 | `probe_fan.swift:18-40` | 扫 page `0xFF00/0xFF08/…` × usage 1-8，得 82 个 distinct Product（`PMU tdie*/TP*/V*/i*`），**fan/rpm/blower 匹配 = NONE** |
| ⑤ 唯一 "fan" 字符串 | `ioreg -l \| grep -i fan` | 只有 `pmgr@8E080000` 节点上的 `"ifane-max"`（4 字节 hex 表），是 **PMGR 电源管理固件表**，非转速 |

**结论**：M1 Pro (MacBookPro18-3) 是带风扇机型，但 macOS 27 完全不把风扇转速暴露到用户态任何免 root 路径。**UI 不出该项**，也不要在设置里留空开关。

**顺带的 PMU 裸电压 / 电流同样不可得**：`AppleSMCKeysEndpoint` 下有 100 个 `AppleARMPMUPowerSensor`（`PMU VP0u`/`vbuck0-10`/`vldo0-11`/`ibuck`/`ildo`），但事件全空 —— `probe_evsweep.swift` 对 page `0xFF08` usage 2（46 个电流传感器）与 usage 3（54 个电压传感器）穷举 event type 0-60 + `IOHIDEventGetIntegerValue`，**全部 nil / 0**；同一次探测里 page `0xFF00` usage 5 的温度传感器 type=15 **正常返回 40.3264**，证明探测方法本身有效（不是方法错）。能拿到的电压只有下一节的「状态名」。

### 2.7 P 核 P-state 驻留（IOReport CPU Stats）

探针 `probe_ioreport.swift`（组内 22 通道，成本 **1.21 ms**）。`PCPU000` 共 16 个状态：

```
PCPU000: V14P0=29.42%  V8P6=8.14%  V7P7=7.19%  IDLE=45.96%  (其余 12 态为小尾巴)
```

负载验证（`probe_load.swift`，8 线程 CPU 压 2 s）：主态从 `V5P9` 迁到 `V6P8`，可复现。

- 状态名 `V<电压档>P<性能档>`，语义是**驻留占比**不是频率绝对值。
- 32 态（P+E）太多，320pt 面板必须聚合为 **IDLE / 低频 / 中频 / 高频 4 档**才画得下。
- `ECPU`: `V4P0=42.4%`；复合体 `PCPM`: `V6P8=20.2%` `V14P0=4.8%`。E 核 / 复合体属于 P2（信息密度低）。
- **CPU 频率绝对值仍不可得**：`hw.cpufrequency = nil`，9225 个 IOReport 通道里 `freq` 只有 8 个命中且全是 ISP 无关项，**没有 CPU 频率通道**。所以 UI 不能写「3.2 GHz」，只能写「高频 29%」。

### 2.8 SoC 电压（IOReport PMP Volt-Temp HM）

探针 `probe_pmpstate.swift`。状态名格式就是 **`<电压mV>_<温度°C>`**，253 个联合态：

```
E0_V_T n=253: 0_0=16.0% 650_65=7.6% 650_75=7.1% 675_65=6.1% 750_65=4.6% 850_65=22.3% 850_75=24.7%
P0_V_T n=253: 0_0=4.5% 800_65=14.6% 825_65=15.7% 875_65=9.3% 975_65=28.8% 975_75=27.1%
G0_V_T n=253: 0_0=53.8% 650_35=3.1% 650_65=42.6% 700_65=0.5%
```

负载验证（8 线程 CPU 压 2 s）：

```
IDLE  P0_V_T: 725_65 @ 30.8%   P1_V_T: 750_65 @ 23.3%   E0_V_T: 850_65 @ 36.7%
LOAD  P0_V_T: 750_65 @ 25.6%   P1_V_T: 775_65 @ 15.6%   E0_V_T: 850_65 @ 39.5%
AFTER P0_V_T: 725_65 @ 39.3%   <- 回落，可复现
```

**坑**：`IOReportSimpleGetIntegerValue` 对这些通道返回 `Int64.min`（`-9223372036854775808`），必须走 `IOReportStateGet*` 系列。全 232 通道一次扫 7.89 ms；只用前 12 个主态可降到 ~2 ms。语义是联合态、没有连续量纲，**只适合进 tooltip，不画曲线**。

### 2.9 屏幕状态与显示

| 项 | API | 实测 | 成本 |
|---|---|---|---|
| 亮 / 灭 / 在线 | `CGDisplayIsActive/IsAsleep/IsOnline` | **1 / 0 / 1** | 0.042 ms（三连） |
| 分辨率 / 刷新率 | `CGDisplayCopyDisplayMode` | 逻辑 1512×982、物理 3024×1964、**120.0 Hz** | 0.10 ms |
| 亮度 | `DisplayServicesGetBrightness`（私有） | **rc=1000, value=−1.0**，`CanChangeBrightness=false` | — |

- `CGDisplayModeGetPixelWidth` 已废弃，用 `.pixelWidth` 属性。
- 亮度在 Apple Silicon 内置屏拿不到（私有 API 直接返回 −1），**不做**。

### 2.10 磁盘健康

```
IOBlockStorageDevice count: 2    NVMe SMART Capable = 1
IONVMeController count: 1        AppleNANDStatus = Ready
IOMedia count: 20                (SMART/health-ish: 无)
```

**坑**：`SMART Capable=1` 只表示「支持」，**没有任何 SMART 属性值**（无 `Temperature` / `Wear` / `LifeLeft`）；`AppleNANDStatus=Ready` 是**静态枚举**，不随健康度变化。→ 只能给「Ready / 不可用」二值徽标，**画不出健康度曲线**。

### 2.11 其它常见项

| 项 | 值 | 坑 |

| 开机时长 | 98868.5 s / 27.46 h | `kern.boottime` 是 timeval，别按 Int64 读 |
| 进程数 | 636（另两次 708 / 673） | `proc_listpids` 两次调用间会变，别当稳定值 |
| swap | 3.22 GB total / 1.90 GB used | pagesize 取 `xsu_pagesize`(=16384) |

## 四、采样预算

按本机实测加总。原则与第一批一致：**高频项压到 1 s 以内总成本 <5 ms，低频项降周期而不是减精度**。

| 周期 | 指标 | 单次成本 | 均摊 ms/s |
|---|---|---|---|
| 1 s | CPU 每核 | 0.007 ms | 0.007 |
| 1 s | 内存 | 1 ms 级 | 0.001 |
| 1 s | 磁盘读写 | 0.256 ms | 0.256 |
| 1 s | GPU 利用率 | 0.041 ms | 0.041 |
| 1 s | 负载 loadavg | 0.0068 ms | 0.007 |
| 1 s | **IOReport Energy Model（新增）** | 1.76 ms | 1.760 |
| 1 s | **进程 Top-N（新增）** | 1.31 ms | 1.310 |
| 5 s | 电池 / 电源适配器 | 1.44 ms | 0.288 |
| 5 s | SoC 温度（4 传感器） | 3.61 ms | 0.722 |
| 5 s | Wi-Fi 链路 | 3.24 ms | 0.648 |
| **合计** | | | **≈ 5.1 ms/s → CPU 占用约 0.5%** |

补充：

- PMP 电压态 7.89 ms / P-state 1.21 ms 建议 **10 s 一次**（均摊 <0.9 ms/s），或按需（用户展开详情）才采。
- 进程全量扫 1.31 ms 已包含 `proc_listpids` + 455 次 `proc_pidinfo`；若只做 Top-5 也省不掉遍历成本，**不要试图用采样进程子集来优化**。
- 所有系统调用必须在后台串行队列执行，跨队列只传 Sendable 值类型（沿用现有 `SystemMonitor` 的调度范式）。

## 五、落地建议

| 优先级 | 指标 | UI 形态 | 理由 |
|---|---|---|---|
| **P0** | GPU 功耗（0.29–2.56 W） | 面积图 / 双线图（与 GPU 利用率同 X 轴） | 已有 GPU 卡，加一条曲线零新增区块 |
| **P0** | 进程 Top-5 CPU% + 内存 | 横向条形图（单色条 + 数值） | 用户最高频诉求「什么卡了」，1.31 ms 成本极低 |
| **P0** | 负载 1/5/15 | 三线折线（复用现有 60 点历史环） | 0.0068 ms，几乎免费，补排队压力 |
| **P0** | 电池循环 / 电量 / AC | 环形 + 徽标（复用内存环形组件） | 笔记本刚需，1.44 ms |
| **P1** | Wi-Fi RSSI / 噪声 | 双线图（同轴 dBm） | 与现有网络模块同域；3.24 ms 需降到 2–5 s |
| **P1** | P 核 P-state 驻留 | 堆叠柱 / 热力条（16 态聚合 4 档） | 32 态进不了 320pt |
| **P1** | VPN 状态 + 屏幕亮灭 | 徽标点（非图表） | 语义型状态，不适合曲线 |
| **P2** | SoC 电压（PMP） | 不画图，只进 tooltip | 「电压_温度」联合态，无连续量纲 |
| **P2** | 磁盘健康 | 不画图，只给 Ready 徽标 | 二值，无趋势 |
| **P2** | 开机时长 / 进程数 | 纯文本行 | 无趋势价值 |

**不做清单**（已在 §3 给出证据）：整机功耗、风扇转速、CPU 频率绝对值、GPU 温度、SSID/BSSID、屏幕亮度、TCP 连接数、`proc_pid_rusage`、电池健康度百分比。
