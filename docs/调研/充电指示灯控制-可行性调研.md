# Mac 充电线指示灯 · 可行性调研

> 目的：判断 toolbar 能否关闭 MacBook 的 MagSafe 充电指示灯（小绿灯），并给出可落地的实现路径与风险边界。调研时间：2026-10；本机实测环境为 MacBook Pro 14"（M1 Pro，MacBookPro18,3），macOS 27.0.1，固件 `20457.1.29`。

## 一、速览结论

1. **可以关，且已实机验证**：MagSafe 指示灯由 SMC 的 `ACLC` 键控制，本机该键**存在且可写**（`size=1, type=ui8, attr=0xd4`）。root 下实际写入 `0x01` 后灯熄灭；实测**唯一会回弹的场景是重新插入充电线**，稳定态、拔线、休眠唤醒均保持熄灭。
2. **必须 root**：非 root 写 `ACLC` 返回 `kIOReturnNotPrivileged`（`0xE00002C1`），写入失败。这是唯一的硬性门槛。
3. **需要常驻特权进程，但职责收窄**：实测证明系统不会在充电状态变化或休眠唤醒时高频改写，daemon 的核心职责就是**监听"插入充电线"事件并强制重写**（对应 `IOPSNotificationCreateRunLoopSource`），辅以唤醒重写与低频巡检兜底即可，不必高频轮询。
4. **与 batt 的差异不影响我们**：`batt` README 称 macOS 27 / 20xxx 固件下其 MagSafe LED 功能不可用，原因是它需要"镜像充电状态"（绿/橙/灭）。我们只做**强制关闭**，不依赖知道充电状态；本次实测已直接证明该固件下强制关闭可用。

## 二、机制与实测证据

### 2.1 `ACLC` 键语义

| 值 | 含义 |
|---|---|
| `0x00` | 系统自动控制（默认，按充电状态显示绿/橙/灭） |
| `0x01` | 强制关闭 |
| `0x03` | 绿灯（充满） |
| `0x04` | 橙灯（充电中） |

`0x05`/`0x06`/`0x07`/`0x19` 为各类错误指示，正常场景用不到。

### 2.2 本机实测（只读探测 + 写回原值）

```
sizeof(SMCKeyData_t)=80
#KEY: size=4  type=ui32  attr=0x80   value: 00 00 08 83
ACLC: size=1  type=ui8   attr=0xd4   value: 03          ← 指示灯由 SMC 控制，可写
AC-W: size=1  type=si8   attr=0x90   value: 04
CHIE: size=1  type=hex_  attr=0xd4   value: 00
CH0B/CH0C/CH0I/ACEN/CHTE: result=132  (key absent)
bfF0: call1 kr=0xe00002c1            (macOS 27 代固件新增的固件限流键，非 root 不可读)
```

- `attr=0xd4` 中可写位已置位，说明该键支持写入。
- 连续采样 3 次（间隔 2s）值恒为 `0x03`，未观察到系统主动改写，说明系统仅在充电状态切换时才动它。
- 非 root 写回原值 `0x03`（**不改变视觉状态**）返回 `kr=0xe00002c1 smcResult=0 FAILED`，确认写权限门槛为 root。

### 2.2.1 实机灭灯验证（root 写入成功）

用移植自 MagHue 的 SMC 实现（`~/.ledexp/ledexp`）在 root 下实际写入并持续采样：

```
23:03:21 写入前: ACLC=0x04 amber(橙)  电量 72%  AC=是  充电中=否
→ 已写入 off(熄灭)
23:03:22 写入后: ACLC=0x01 off(熄灭)  电量 72%  AC=是  充电中=否
```

**持续 55 秒采样结果：`ACLC` 全程稳定为 `0x01`，未被系统改写。**

中途发生了一次充电状态翻转（`充电中=否` → `充电中=是`，第 6 次采样），**该翻转并未触发 `ACLC` 回写**：

```
[5] 23:04:16 ACLC=0x01  电量 72%  充电中=否
[6] 23:04:22 ACLC=0x01  电量 72%  充电中=是   ← 状态翻转，键值不变
[10] 23:04:46 ACLC=0x01  电量 72%  充电中=是
```

结论对实现架构有直接影响：

- **写入确实生效**，`0x01` 能压住系统默认显示，本机 20xxx 固件不存在 batt 所述的"LED 功能不可用"问题（那是它需要镜像充电状态导致的设计限制，与本方案无关）。
- **系统并非高频改写**，至少充电状态翻转不会重置它。因此 daemon 不需要高频轮询。
- 但写入前读到 `0x04`（橙），说明**系统原本在驱动该键**；休眠唤醒、脱插重插、SMC 重置等边界仍可能夺回控制权，daemon 仍有必要，只是可低频巡检 + 事件驱动重写。

> 未验证的边界：休眠唤醒后是否回弹、拔插充电线后是否回弹、重启后是否保持。这三项需后续实测（见 4.2）。

### 2.3 与其他方案对比

| 方案 | 能否关闭 | 门槛 | 说明 |
|---|---|---|---|
| SMC `ACLC` 直写 | ✔ | root | 本文推荐路径，本机已验证键存在可写 |
| [MagHue](https://github.com/kamenlevi/MagHue) | ✔ | root + 安装 daemon | **与我们要做的形态最接近**：开源（GPL-3.0）、菜单栏 App + root daemon、三模式含 *Off*。全量源码已逐行核对，是最佳参考实现 |
| [batt](https://github.com/charlie0129/batt) `magsafe-led always-off` | ✔（旧固件） | root + 安装 daemon | 本机 20xxx 固件下该子功能被上游标记不可用；只写 `ACLC` 的部分仍可借鉴 |
| AlDente Pro | ✔ | root + 商业授权 | 有 MagSafe LED 控制，闭源，且**会与我们的 daemon 抢同一个键**（见 3.4） |
| 系统设置 / 官方 API | ✘ | — | Apple 未提供任何公开 API |

> 注：没有搜到名为 `magled` 的 macOS 工具；同领域实际存在的是 MagHue、MagSleep、batt、AlDente，其中 MagHue 的 README 与我们的需求几乎逐字对应。

## 三、toolbar 落地路径

### 3.1 架构（推荐）

```
NetworkMonitor.app（普通用户权限，菜单栏 UI）
        │  XPC（NSXPCConnection）
        ▼
com.example.NetworkMonitor.ledhelper（root LaunchDaemon，开机自启）
        │  IOServiceOpen(AppleSMC) + SMC 写
        ▼
    SMC 键 ACLC = 0x01
```

- 守护进程负责：开机设置 `0x01`、监听充电状态变化（IOPS）后重新写入、休眠唤醒后重新写入。
- 主 App 只通过 XPC 发"开/关/查询"指令，不直接持有 root 能力，遵循最小权限。
- 安装方式：`SMAppService.daemon(plistName:)` 注册（macOS 13+），需要开发者签名。

### 3.2 关键实现点

- SMC 调用使用 `IOConnectCallStructMethod`，`SMCKeyData_t` 必须是 80 字节的标准布局；**本机实测布局写错时连 `#KEY` 都读不到**（返回 `result=132`），这是最容易踩的坑。
- 写入按 1 字节 `ui8` 处理：`data8 = 6`（`SMC_CMD_WRITE_BYTES`），`bytes[0]` 填目标值。
- 关闭后需保证"回得来"：提供"恢复系统控制"入口，写回 `0x00`。

### 3.3 MagHue 源码核对出的关键坑（已逐行确认）

MagHue 是此需求最成熟的参考实现，其 daemon 处理了几件容易漏掉的事，建议直接沿用：

| 问题 | MagHue 的处理 | 对我们的含义 |
|---|---|---|
| **休眠期间脱插** | 休眠时进程不运行，线缆重新插拔会把 LED 交回固件，整夜按系统色亮 | 必须监听唤醒事件（`IORegisterForSystemPower` + `systemHasPoweredOn`）后立即重写 |
| **唤醒消息应答** | 收到 `canSystemSleep` / `systemWillSleep` 立刻 `IOAllowPowerChange` | 不应答会让整机卡住 30s 直到超时，**必须应答** |
| **外部应用抢键** | 每轮巡检读取实际值，与期望不一致即视为 drift 并重写 | AlDente Pro 也写 `ACLC`，只"变化才写"会永久输掉争夺 |
| **未插电时是"幽灵"** | 仅在 AC 供电时才做 drift 检查 | 拔掉充电线后键保留最后值且写入不生效，"重写"会空转一整天 |
| **插线确认手感** | 插上瞬间显示真实色（橙/绿）5s–1min 再回到目标态 | 强制灭灯会丢掉"磁吸是否吸稳"的唯一反馈，建议抄这个 grace window |
| **关机/卸载** | 收到 SIGTERM/SIGINT 时写回 `0x00` 交还系统 | 不留"灯永久不亮"的脏状态 |
| **配置目录权限** | 配置目录 chown 给安装用户，helper 以 root 读取 | 避免每次改设置都要输密码 |
| **旧版安全漏洞** | 曾把状态文件放在用户可写目录，任意用户可篡改 → 已迁移到 root 专属目录并校验属主 | 特权进程读写的任何路径都应校验属主，这点要照做 |

其 `SMCParamStruct` 在 `data8` 前**显式插入 `padding: UInt16`**，并断言 `stride == 80` 才允许访问 SMC——这正是我第一次探测失败的原因（布局少了 2 字节 padding）。

### 3.4 与 AlDente Pro 共存

AlDente Pro 的 MagSafe LED 功能写同一个 `ACLC` 键。若两者同时启用会互相覆盖，表现为灯色闪烁或反复横跳。建议在本功能确认启用时，检测 AlDente 是否在运行并提示用户二选一。

### 3.5 风险与限制（务必让用户知情）

| 风险 | 后果 | 缓解 |
|---|---|---|
| 关机后失效 | 关机状态下无法控制 LED | 属硬限制，说明即可 |
| **重新插入充电线回弹** | 灯恢复为橙/绿，用户以为功能失效 | 监听 AC 插入事件强制重写（已实测为唯一必回弹场景） |
| 休眠/唤醒、SMC 重置 | 本次浅睡未回弹，深睡未覆盖 | 唤醒事件后重写一次兜底 |
| 与系统充电指示冲突 | 强制关闭后用户看不到充电异常提示 | 在 App 内以图标/通知补位充电状态 |
| 需要 root 守护进程 | 增加安装与签名复杂度，用户需授权 | 仅在用户显式开启该功能时注册 |
| 系统升级 | SMC 键可能变化 | 启动时探测 `ACLC` 是否存在，不存在则降级隐藏入口 |

## 四、建议

1. ~~先做最小可用验证~~ **✅ 已完成**：root 下写入 `0x01` 生效，灯熄灭并稳定保持。剩余边界（休眠唤醒、拔插、重启）需在实现阶段补测，见 4.2。
2. **能力探测优先**：参照 batt 的做法，运行时探测 `ACLC` 是否存在来决定是否显示该功能入口，不要按 macOS 版本或机型硬编码。
3. **本期只关不控**：只提供"关闭指示灯 / 恢复系统控制"两项，不做绿橙镜像，避免陷入 batt 在 20xxx 固件上遇到的"无法可靠获知充电状态"问题。

### 4.1 代码落点（对照本项目结构）

| 组件 | 建议位置 | 说明 |
|---|---|---|
| SMC 客户端 | `NetworkMonitorCore/Infrastructure/SMC/` | `SMCParamStruct`（80 字节含 padding）、`readByte` / `writeByte`、`keyInfo` 探测；纯逻辑可进 TestRunner |
| LED 语义封装 | `NetworkMonitorCore/Infrastructure/MagSafeLed.swift` | `system/off/green/amber` 枚举 + `isSupported()`，与 SMC 字节解耦 |
| 电池状态 | `NetworkMonitorCore/Infrastructure/BatteryMonitor.swift` | `IOPSCopyPowerSourcesInfo` 读百分比与充放电态（参考 MagHue `Battery.swift`） |
| 特权守护进程 | 新增 `Sources/NetworkMonitorLedHelper/` | 独立 executable target，launchd daemon，`RunAtLoad` + `KeepAlive` |
| 安装/卸载脚本 | `NetworkMonitor/Scripts/install-led-helper.sh` | 由 App 经 `NSAppleScript`「以管理员身份运行」调起，模板见 MagHue `install-helper.sh` |
| UI 开关 | `Sources/NetworkMonitor/MenuPanel/SystemPaneView.swift` | 跟随现有「开机自启动」条目的交互形态，避免新造控件 |

注意：本项目当前为 ad-hoc 签名（`codesign --sign -`），没有 Apple Developer ID。`SMAppService.daemon` 在 ad-hoc 签名下的行为需实测；MagHue 的替代做法是**脚本 + `/Library/LaunchDaemons` + `NSAppleScript` 提权**，不依赖签名，落地风险更低，建议优先采用。

### 4.2 边界场景实测结果

灭灯已实证可用，边界场景也已实测，**仅剩重启未测**：

| 边界场景 | 实测结果 | 时间线证据 |
|---|---|---|
| 稳定充电中 | ✅ 保持熄灭 | 55 秒采样，期间充电状态翻转（否→是）也未改写 |
| 拔掉充电线 | ✅ 保持熄灭 | `23:07:20 AC=否 ACLC=0x01` |
| **重新插入充电线** | ❌ **回弹为橙** | `23:07:34 AC=是 ACLC=0x04` |
| 休眠 → 唤醒（11 秒浅睡） | ✅ 保持熄灭 | `23:12:37 Entering Sleep` → `23:12:48 Wake` → `23:14:15 ACLC=0x01` |
| 重启 | ⏳ 未测 | — |

**关键结论：唯一确认会回弹的场景是「重新插入充电线」。**

这个结果比 MagHue 的经验更乐观（它认为休眠、插拔都会回弹），但实现上仍有两点必须照做：

1. **监听 AC 插入事件并强制重写**——这是 daemon 的核心职责，对应 `IOPSNotificationCreateRunLoopSource`。检测到 `onAC` 由假变真时，无条件重写 `0x01`（不能"值没变就跳过"，因为插拔后系统会先改写）。
2. **唤醒后仍建议重写一次**——本次 11 秒浅睡未回弹，但长时间深休眠、以及休眠期间拔插再唤醒的组合场景未覆盖，按 MagHue 的做法注册 `IORegisterForSystemPower` 更稳妥。

**采样方法**：非 root 持续采样 `ACLC` 与电源状态至 `/tmp/aclc_timeline.log`（`~/.ledexp/aclclog`），每 2 秒一次、值不变时去重，用于还原事件时序。
