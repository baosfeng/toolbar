## 结论摘要

1. **下载进度：一条字节级回调都没有，不是「有代理没接到 UI」**。全仓 `grep 'URLSessionDownloadDelegate|didWriteData|bytesWritten'` = **0 命中**；`UpdatePackageDownloader.downloadPackage` 返回整体 `Data`（`UpdatePackageDownload.swift:75,100-112`），最终落到 `session.data(for:)`（`HTTPTransport.swift:76`）——一个「发出去、等整包回来」的原子调用，中途没有任何可观测点。
2. **四段里只有 4 个「阶段打点」，全部在段边界，段内静默**：`UpdateInstallPhase`（`UpdateInstaller.swift:9-18`）只有 downloading / verifying / installing / readyToRelaunch 四档，分别在 `:98 / :109 / :138 / :181` 打一次。下载这一整段（线上清单实测 12,792,314 字节 ≈ 12.2 MB、超时上限 60 秒，`UpdatePackageDownload.swift:82`）**全程只对应屏幕上静止的一句「正在下载安装包…」**。
3. **界面表现 = 纯静态文案**。安装卡三行（`SettingsAboutUpdateParts.swift:52-53,109-111`）：状态标签显示「正在下载安装包…」（`UpdateInstallLogic.swift:85-86`）、按钮标题变「下载中…」并置灰（`:106,115-119`）、说明行换「安装过程不会中断当前使用；失败会保留原版本。」（`:127-128`）。没有百分比、字节数、速度、剩余时间，也没有任何阶段列表。
4. **失败有可见反馈但只有一行**：`.failed` → 「安装失败（原因）」（`UpdateInstallLogic.swift:93-99`），状态标签切 `warnInk` 告警色（`SettingsAboutUpdateParts.swift:123`），说明行切「重启后可能需要重新授权」（`:125-126,128-130`）。失败原因塞在同一行，长原因会被行宽压缩。
5. **新版本信息只展示了 3 个字段**（当前版本 / 最新版本 / 说明正文），缺 **发布日期 / 包大小 / SHA-256 / 下载地址 / 选中架构包名 / 安装目标路径**。值得注意的是后两个字段 Core 已经解析出来了却没人消费：`UpdateArtifact.byteCount`（`UpdateManifest.swift:17`）只被 `UpdatePackageTarget` 透传（`UpdatePackageSelection.swift:57,63,99`）、`UpdateManifest.minimumSystemVersion`（`UpdateManifest.swift:53`）**全仓零消费者**；`UpdateRelease.publishedAt`（`UpdateChecker.swift:17`）只在 TestRunner 探针里打印过（`UpdateCheckerLiveProbe.swift:47`）。
6. **说明区固定 132pt 可滚动**（`SettingsReleaseNotesView.swift:18,59`），关于页内容实测总高 **约 830pt**、可视区 **540pt**、**已溢出约 290pt**（见下文实测表）。所以新增进度区不是「挤掉谁」而是「把滚动距离再拉长」；真正的坑是**进度区落在视口外**，用户点完按钮更看不到了。
7. **推荐方案（三段式）**：阶段列表（下载/校验/解包/换包/重启 5 行，当前高亮）+ 只有下载段给确定性进度条（其余段走不定态）+ 一行详情（已下 / 共 / 速度 / 剩余）。落地位置在「安装」卡 `statusRow` 之下，安装开始时自动滚到该卡可见（`SettingsPageStack` 目前**没有滚动定位能力**，需补一个入口）。
8. **不需要新偏好键**：进度是运行期瞬时状态，不属于偏好；唯一候选「安装完成后自动重启」目前是硬编码的 0.6 秒后 `terminate()`（`UpdateCheckService.swift:145-146`），不在本次范围内。
9. **一个必须先解决的架构冲突**：`HTTPTransport.send`（`HTTPTransport.swift:53-55`）是全仓唯一出网口且**没有进度通道**。要拿字节进度，要么给 transport 加流式子能力（推荐），要么让下载器绕开它直连 URLSession（违反「出网只走 HTTP」的唯一出口纪律，不推荐）。
10. **线上清单实测（2026-11-25 拉取真实 `update.json`）**：`tag=v1.31.0`、`publishedAt=2026-11-24T15:38:39Z`、`asset.byteCount = 12792314`（**约 12.2 MB**）、`sha256` 64 位齐全、**`platforms` 表为空**（1.31 尚未发单架构包）。也就是说当下真实用户点「下载并安装」要下的就是这 12.2 MB 的 universal 包，**分母现成、无需额外请求**。
11. **进度实现的 API 可行性已从 SDK 证实**：`URLSession.bytes(for:delegate:)` 在 `Foundation.swiftinterface` 里位于 `@available(macOS 12.0, ...)` 的扩展内（SDK `MacOSX.sdk/.../arm64e-apple-macos.swiftinterface:16721-16722`），项目最低 macOS 14 → **可直接用**，不必引入 delegate 或临时文件。
12. **改 `HTTPTransport` 的波及面很小**：全仓只有 **1 个真实实现**（`URLSessionHTTPTransport`，`HTTPTransport.swift:60`）+ **1 个测试替身**（`RecordingTransport`，`TestRunner/HTTPTransportTests.swift:260`）。加带默认实现的新方法不会迫使任何调用方改动。

### 8. `NetworkMonitorCore/Update/UpdateChecksum.swift`（26 行）—— 一次性哈希

## 可实现的进度通道（下载 / 校验 / 解包 / 换包 四段各有几个可观测点）

### 段 1：下载（占墙钟 70–90%）

| # | 可观测点 | 数据来源 | 改动位置 | 确定性 |
|---|---|---|---|---|
| D1 | 已接收字节 / 总字节 | `URLSession.downloadTask(_:didWriteData:totalBytesWritten:totalBytesExpectedToWrite:)` | `HTTPTransport.swift:76` 换实现 | ✅ 确定 |
| D2 | 总字节（分母） | `URLResponse.expectedContentLength`（GitHub CDN 有 Content-Length）或清单 `artifact.byteCount` | 同上 / `UpdatePackageSelection.swift:57` | ✅ 两者都有，取先到者 |
| D3 | 瞬时速度 | `Δbytes / Δt`（滑动窗口 1–2 秒） | 新增纯函数（放 UI 库可测） | ✅ 自算 |
| D4 | 剩余时间 | `(total - written) / speed` | 同上 | ⚠️ 估算，前期抖动大（建议 <5% 不显示） |
| D5 | 下载重定向后的最终 URL | `task.currentRequest.url` | 无需展示 | — |
| D6 | 阶段切换 | 现有 `.downloading` 打点 | `UpdateInstaller.swift:98` | ✅ 已有 |

**替代实现（推荐）**：`URLSession.bytes(for:)` 拿 `AsyncBytes` 逐块累积 + 自计字节数，无需 delegate、无需临时文件。**已从 SDK 证实可用**（`@available(macOS 12.0, ...)`，见 `Foundation.swiftinterface:16700-16722`，项目最低 14），且 `AsyncBytes.task` 是公开的 `URLSessionDataTask`，取消语义齐全。不引入 `NSObject` 子类、不破坏 `HTTPTransport` 的值语义。

推荐签名（加默认实现，旧替身零改动）：
```swift
public extension HTTPTransport {
    /// 带字节进度的下载 —— 默认退回原子实现（旧替身无需实现即可编译）
    func download(_ endpoint: Endpoint<Data>,
                  progress: @Sendable (_ received: Int64, _ expected: Int64?) -> Void) async throws -> Data {
        try await send(endpoint)
    }
}
```

**注意**：`(data, response) = try await session.data(for:)` 改成流式后，`HTTPResponse` 的构造（`HTTPTransport.swift:86-90`）需要等全部收完才能判非 2xx——**非 2xx 的流式响应必须先读完/丢弃再抛**，否则 403 页面会被当成安装包字节累加。这是实现时最容易踩的坑。

### 可扩展位置：三个候选

**方案 A（推荐）：安装卡内、`statusRow` 之下插一整行「进度区」**

```
安装卡
├── statusRow              「安装」 [正在下载安装包…]  [下载中…]  ← 现有
├── progressRow            ← 新增，整行宽（与 notesRow 同构，不是 SettingsRowView）
│   ├── 阶段列表 5 行 × 18pt = 90pt（含勾/高亮/灰三态）
│   ├── 进度条 6pt + 4pt 间距（只在下载段显示，其余段转圈）
│   └── 详情行 14pt（「已下载 6.2 MB / 12.4 MB · 2.1 MB/s · 剩余约 3 秒」）
├── autoRow                「自动下载安装」[开关]                    ← 现有
└── noteContainer          说明段                                  ← 现有
```

高度账：
- 完整进度区（阶段列表 + 条 + 详情）= 90 + 10 + 14 + 上下 padding 8 ≈ **122pt**
- 只做「条 + 详情」紧凑版 = 6 + 4 + 14 + padding 8 ≈ **32pt**
- **推荐紧凑版起步**（32pt）→ 溢出 290 → **322pt**；`idle` 态完全隐藏该行（高度 0），只有 busy / failed 时出现。

**方案 B（组合推荐）：安装期把「新版本说明」从 132pt 压到 80pt，腾 52pt 给进度区**

理由：安装一旦开始，说明区已经不是用户关心的信息（用户已经在装那一个版本了），而进度才是。
- 净增 32 − 52 = **−20pt**（反而少滚一点）
- 实现：`SettingsReleaseNotesView.contentHeight` 由常量改成可变（`var compactHeight: CGFloat?`），安装期由 pane 设 80pt。
- **代价**：说明区高度会跳变，需要一次 `NSAnimationContext` 或直接瞬时改（设置窗口内瞬时改可接受）。

**方案 C（不推荐）：把进度塞进「状态」行**

`statusLabel.stringValue` 改成「正在下载 42%（5.2 / 12.4 MB）」。改动最小（1 行文案），但：
- 行宽只有 ~200pt（660 可用 − 标题 − 按钮），42% 那串会被压缩
- 没有阶段感，用户仍然不知道「还要多久、在做什么」
- 与既有的「右对齐值标签」语义冲突（值标签是状态，不是进度）

**推荐组合：A（紧凑版）+ B（安装期压缩说明区）+ 安装开始时滚动定位。**

## 风险与依赖

### 架构风险

1. **`HTTPTransport` 是「全仓唯一出网口」（`HTTPTransport.swift:47-55` 注释明写「除局域网文件流外，全仓只此一个实现」）**。加流式下载能力必须改这个协议，但**波及面实测很小**：全仓 1 个真实实现（`URLSessionHTTPTransport`，`HTTPTransport.swift:60`）+ 1 个测试替身（`RecordingTransport`，`TestRunner/HTTPTransportTests.swift:260`）；13 个 provider 只以 `any HTTPTransport` 持有类型，不实现协议，**不受影响**。**推荐做法**：给协议**新增**一个带默认实现的方法
   ```swift
   public extension HTTPTransport {
       func download(_ endpoint: Endpoint<Data>,
                     progress: @Sendable (Int64, Int64) -> Void) async throws -> Data {
           try await send(endpoint)          // 默认退回原子实现，旧替身零改动
       }
   }
   ```
   只有 `URLSessionHTTPTransport` 覆写成流式。这样「唯一出口」纪律不破，测试替身也不用全改。

2. **非 2xx 的流式响应会污染字节计数**（见段 1 的坑）。流式实现必须先看 `HTTPURLResponse.statusCode`，非 2xx 时丢弃已收字节、走 `errorMapper`。

3. **`Task { }` 与主线程**：`UpdateCheckService` 是 `@MainActor`（`:18`），`Task { ... }`（`:133`）继承 MainActor。但 `UpdateInstaller.install` 是 `nonisolated async`（`UpdateInstaller.swift:93`），按 SE-0338 会跳到 cooperative pool → **同步 IO（`write` / `ditto` / `waitUntilExit`）不在主线程，界面不会被冻住**。
   - ⚠️ **但加了高频进度回调后**，`Task { @MainActor in self.apply(...) }`（`UpdateCheckService.swift:138-140`）会按网络包频率往主线程投递。**必须节流**（推荐 ≥100ms 一次，纯函数 `UpdateProgressThrottle.shouldEmit(last:now:)` 放 UI 库可测），否则设置窗口滚动会抖。
   - **此条为静态推理，未真机验证**（见「未验证」）。

4. **进度必须落在 service，不能落在视图**：`SettingsWindow.select` 每次重建 pane（`SettingsWindow.swift:133-149`）。如果把 `lastProgress` 存在 `SettingsAboutInstallCard` 里，用户切到「通用」再切回来进度归零。

5. **失败态的进度残留**：`.failed` 时应保留「卡在哪一段」（现有 `failureReason` 只有一句中文，没有阶段）。推荐 `UpdateInstallState` 加 `lastStage: UpdateInstallStage?` 或让 `failureReason` 与 `stage` 并存（现有设计 `stage == .failed` 时阶段信息已丢失，`UpdateInstallLogic.swift:29-30` 的注释说「失败同时保留卡在哪一步」——**代码与注释不符，注释描述的能力尚未实现**）。

### 依赖

- **无新三方依赖**。SHA-256 已用 CryptoKit（`UpdateChecksum.swift:1`）。速度 / 剩余时间格式走现有 `ByteFormatting`（`Infrastructure/Formatting/ByteFormatting.swift`）与 `SystemDetailFormatting.byteCountText`（`SystemDetailFormatting.swift:43-58`），**不要另写单位换算**。
- **进度条控件**：本仓无现成进度条（`grep NSProgressIndicator` = 0 命中），但设置页是普通 NSView 体系，可直接用 `NSProgressIndicator(style: .bar)`（设置窗口不套玻璃，不需要自绘）；也可以用现成的自绘条思路参考 `SystemStackedBarView`（`MenuPanel/SystemRingView.swift:75`）。
- **可测性**：阶段 → 文案的派生必须放 `NetworkMonitorUI`（TestRunner 只依赖 Core + UI，`toolbar-coding-standards` 明写「App 可执行 target 无法被 TestRunner import」）。现有 `UpdateInstallText`（`UpdateInstallLogic.swift:74-135`）就是这条范式的样板，新增 `UpdateProgressText` 照抄。

### 偏好键

**不需要新增偏好键。** 理由：
- 进度是运行期瞬时状态，重启即无意义；
- 现有 `update.lastCheckAt`（`UpdateCheckPreferences.swift:15`）与 `update.autoInstall`（`:46`）已覆盖「检查节奏」与「自动安装」两个可持久化的维度；
- 唯一反例是「安装完成后是否自动重启」—— 当前是硬编码 0.6 秒后 `terminate()`（`UpdateCheckService.swift:145-146`），如果要做成开关需要新键 `update.autoRelaunch`（默认开），但**这不在用户诉求内**。

### 另一个值得注意的产品缺口（本次不做，但要说清）

**自动安装开启时用户完全在流程外**：`UpdateCheckService.swift:118-121` 命中新版本且 `autoInstallEnabled` → 直接 `install()`。如果用户此时不在设置页（甚至不在 app 里），**全程零反馈，然后应用突然重启**。这是比「看不到进度」更严重的体验问题。可能的出口（择一）：
- 菜单栏状态项临时显示进度（改动大，涉及 `MenuBarManager` 的 17 指标体系）
- 一条「正在安装更新」的系统通知（走 `NotificationServicing`，与现有七类事件并列，需要新增 `NotificationEvent` case → 按扩展点清单要补 5 个 switch + `NotificationCue`）
- 默认把自动安装开关的副标题写死「开启后应用会在后台自行重启，界面不显示进度」

推荐第三条（零改动、诚实告知），若用户要求再走第二条。

## 未验证

以下结论有静态推理依据但**未在真机跑通**，实现前需要补证：

1. **【主线程是否被同步 IO 阻塞】** 依据是 SE-0338（nonisolated async 函数不在调用方 executor 上跑）。未实测：点「下载并安装」期间设置窗口是否可滚动 / 是否出现彩虹球。验证方法：拿一个大版本（`dist/` 里造 100MB 假包）跑一遍，同时 `sample 一览 3` 看主线程栈。**如果不成立，改动方案要先加 `Task.detached` 或把同步 IO 挪到 `DispatchQueue`。**
2. **【`URLResponse.expectedContentLength` 是否可用】** GitHub Releases 的 `browser_download_url` 是 302 → `objects.githubusercontent.com`，理论上带 `Content-Length`。未实测该 endpoint 的实际响应头。若拿不到，分母只剩清单 `byteCount`（有些旧发布没有）。
3. **【`URLSession.bytes(for:)` 在 macOS 14 的可用性与行为】** ✅ **可用性已证实**：SDK `Foundation.swiftinterface` 第 16700 行 `@available(macOS 12.0, iOS 15.0, ...)` 扩展内含 `bytes(for:delegate:)` / `bytes(from:delegate:)`，`AsyncBytes` 是 `AsyncSequence, Sendable`，并暴露 `public var task: URLSessionDataTask`（可用于取消）。⚠️ **仍有两项未验证**：(a) 未在本仓编译过；(b) 未实测它对 12.2 MB 包的内存峰值是否真的低于 `data(for:)`。
4. **【真实下载耗时】** 没有真机跑过从 GitHub CDN 下 12.2 MB 包的实际耗时与速度波动，因此「剩余时间」算法的抖动阈值（建议 <5% 不显示）未标定。**注意这条影响设计选择：若实测总是 <3 秒完成，进度条会一闪而过，届时应把「下载」这一行做成「瞬时高亮一下即打勾」而不是长驻条。**
5. **【关于页溢出 ≈290pt 的精度】** 由 AX 元素 y 坐标推算（「退出」底 952 + 底内边距 16 − 滚动区顶 138 ≈ 830；830 − 540 = 290），误差约 ±10pt（取决于页尾说明是否折成 3 行）。截图里窗口高 572（内容 540 + 标题栏 32），与 `SettingsSkeletonMetrics.windowHeight = 540`（`SettingsSkeletonLogic.swift:18`）一致。**未做像素级核对**。
6. **【`nmcli` 截图里的滚动条位置】** 截图显示滚动条在顶部但内容明显超出，说明滚动区内容高度约束正确；未验证滚到底部时「退出」按钮是否完整可见（AX 报 `920.0` 与可视底 `678` 差距较大，理论上需要滚约 290pt 才见底）。
7. **【当前运行版本与源码是否一致】** 截图显示 1.31.0 / 构建号 24，与 `NetworkMonitor/version.env`（`VERSION=1.31.0` `BUILD=24`）一致；但工作区有未提交改动（`.agents/skills/toolbar-coding-standards/SKILL.md`、`.github/workflows/release.yml`、`AGENTS.md`、`NetworkMonitor/Scripts/build-app.sh`、`file-family-baseline.txt`），**不排除运行的 .app 与当前源码有微小差异**。本报告的行号以当前工作区源码为准。
8. **【`UpdateInstallState.requiresManualInstall` 的实际触发路径】** 代码里只有 `static func manual(_:)`（`UpdateInstallLogic.swift:61-63`）会置 true，但 **grep 全仓没有任何调用点**。这意味着「需手动安装」这条失败话术（`:95-97`）目前是死代码。未验证是否有意保留。
