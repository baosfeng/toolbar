# 打包脚本按名字杀进程会连坐无关进程

> **何时阅读：** 改 `Scripts/build-app.sh` 的部署段；或出现「打包成功但新版本没生效 / 菜单栏出现两个图标」。

## 问题描述

原实现三行：

```bash
RUNNING_PID=$(pgrep -f "${APP_NAME}" || true)
kill "$RUNNING_PID" 2>/dev/null || true
kill -0 "$RUNNING_PID" 2>/dev/null
```

两个独立缺陷叠在一起：

1. **`pgrep -f "${APP_NAME}"` 过宽**：`APP_NAME=NetworkMonitor` 与仓库目录同名，
   任何命令行含该串的进程都会被命中——另一 agent 的
   `swift-build --package-path .../NetworkMonitor/.build`、编辑器语言服务、甚至 shell 自己。
2. **多行 PID 直接喂给 `kill`**：实测 `kill "$(printf '1\n2\n3')"` 报
   `arguments must be process or job IDs`，被 `|| true` 吞掉后脚本认为「没有要杀的进程」，
   继续 `rm -rf /Applications/一览.app`。

> 包名已改为「一览.app」，脚本现在同时扫 `/Applications/一览.app` 与旧路径 `/Applications/NetworkMonitor.app`；上面这条事故是 rename 之前的记录。

后果：旧实例存活并持着已删除的 inode，新 .app 被复制进去，`open` 后新旧两个进程
共用同一个 `monitor.db`，**新版本静默不生效**。

## 解决方案

判据收敛到「可执行文件绝对路径完全一致」，并且逐个 PID 处理、每轮重新查存活：

```bash
running_pids() {
    pgrep -f "^${INSTALL_PATH}/Contents/MacOS/${APP_NAME}( |$)" || true
}
# 逐个 kill；每轮重新 running_pids 复检；仍有存活则 exit 1，不再继续 rm -rf
```

注意 `INSTALL_PATH` 必须在杀进程**之前**定义（原来定义在删除段，函数引用不到）。

## 如何识别

- 打包日志里「正在关闭正在运行的 NetworkMonitor（PID: 12345 67890）」后面还是「删除旧版本」；
- `pgrep -f "^${INSTALL_PATH}/Contents/MacOS/${APP_NAME}( |$)"` 有输出但脚本说没进程；
- 改完代码打包、重启后行为没变——先确认跑到的是不是旧二进制（`ps` 看启动时间）。
