# 菜单面板内存常驻

> **何时阅读：** 怀疑菜单栏进程占内存偏高、要做内存归因、或改动分页装配 / 面板预热时。

## 现象

启动几分钟后进程 `一览` 的 `phys_footprint` 稳定在 140 MiB、`ps` RSS 267 MiB、footprint 峰值 363 MiB，而且**数值稳定不涨**。

两个容易混淆的口径：

| 口径 | 值 | 含义 |
|---|---|---|
| 活动监视器「内存」列 / `footprint` 的 `phys_footprint` | 134–140 MiB | 真实占用（dirty + compressed） |
| `ps -o rss` | 267–309 MiB | 含 AppKit / SwiftUI / 系统库的只读共享页（约 127 MiB），所有进程共用，不算本进程实占 |

用户报「占 300MB」时先确认是 RSS 还是活动监视器内存列，两者不要混着比。

## 归因步骤（按顺序，前一步不够再走下一步）

```bash
pid=$(pgrep -f "/Applications/一览.app/Contents/MacOS/一览" | head -1)

# 1. 真实占用与峰值
footprint -p $pid | head -40            # phys_footprint / phys_footprint_peak + 分类（Malloc Small / CoreAnimation / ...）
# 2. 虚拟内存分布（确认 RSS 大头是不是只读段）
vmmap -summary $pid | sed -n '/REGION TYPE/,/^$/p'
# 3. 对象级归因（海量小对象时看「数量」而不是「字节」，最大单类往往只有几 MB）
heap $pid -sortBySize | sed -n '/COUNT .*BYTES/,+40p'
# 4. 冷启曲线：把「启动即占」和「打开面板后占」分开
#    重启后每 0.8s 采一次 rss + footprint，共 40 次
```

判读要点：

- `leaks $pid` 只报 20 KB 级 → 不是泄漏，是**常驻结构本身大**，别往「有对象没释放」方向查。
- `heap` 里最大单类只有 2 MB 级、但节点数 58 万 → 内存是**海量小对象累积**，要减的是对象数量（视图 / 约束 / layer），不是某个大缓冲。
- `NSImage` 111 个（17 KB）、`CGImage` 240 个（76 KB）→ 图标 / 图片缓存不是大头，别先动那里。
- `_NSViewLayoutAux` 3413、`NSLayoutConstraint` 14214、`NSViewBackingLayer` 2833 → 一个 AutoLayout 满配视图连同 layer 约 10–30 KB，三千个就是 100 MB 级。

## 根因

1. `MenuPanelView.init` 把六个分页一次性 new 出来并全部 `addArrangedSubview` 进 `paneStack`（改前冷启即 **1497 视图 / 10522 约束**）。
2. `AppDelegate` → `schedulePrewarm()` 在启动 1.2 s 后真 `popover.show` 一次再关掉（为把首开 375 ms 挪到点击之前），于是整棵树在启动期就进窗口、完成布局并建 layer。
3. 没有任何回收路径：`MenuPanelController.content` 强持有面板，`popover.contentViewController` 又持有它 → 视图永不 deinit，收起面板也不释放。

冷启曲线能直接看到这三段：0 s 6.5 MiB → 1 s 81 MiB（启动路径）→ 2 s 120 MiB（预热）→ 稳定 140 MiB。

## 处置（2026-11）

| 改动 | 效果 |
|---|---|
| 分页改**懒装配**：冷启只装配当前页，其余页首次切到时才建实例、才进栈、才加宽度约束、才挂动作回调（`MenuPanelView+Panes.swift`） | 冷启结构 1497 视图 / 10522 约束 → **105 / 744**；每页再切一轮总数与改前完全一致、`assemblyCount` 恒为 1（不重复建） |
| 未装配页的数据转发改为「已装配才更新」，切页时由控制器补一次该页全量（`menuPanelViewDidSelectTab`） | 切过去不会空；跳过期间不发尺寸通知 |
| 剪贴板卡片流滑动窗口 120 → 32（`ClipboardCardWindowPolicy`） | 打开过剪贴板历史面板后 footprint −14.4 MiB；面板宽 346 pt，一屏只看得见 1–2 张卡，原 120 张里 88 张纯空占 |
| 图标降采样 / 缩略图预算 64→24 MB | **实测 ≈0 MiB 收益，已回退**（未打开历史面板时这些路径根本不构造） |

冷启 footprint（同机、同一份 release 包、不点开面板）：t=30 s 108 → **90 MiB**，长程 180 s 103.6 → **77.0 MiB**。

## 改动时必须守住的三条

1. **不要在任何初始化路径里直接读 `panel.xxxPane`**（它是懒入口，读到就建）。要判「建没建」用 `paneIfLoaded(_:)` / `xxxPaneIfLoaded`。
2. **未装配分页的数据会被丢弃**，因此每个分页的「切到时补全量」必须真的接上（网络页补流量 / 进程 / Wi-Fi，剪贴板重取，传送 `attach` + `refreshNow`，额度 / Token / 系统各自补一次）。
3. **取证快照路径要显式装配**（`MenuPanelView.evidencePanel()`），否则 `NM_SNAPSHOT_DIR` 渲出来的是「先推数据后切页」的空页。

## 仍未处理的余量

改后剩下的 90 MiB 里，面板只占约 5 MiB，主体是启动路径本身（网络模块 / 系统监控采样 / 数据库与仓储 / AppKit 首帧）。要继续压就往这条链路上做 `heap` 冷启对比，而不是继续减面板视图。
