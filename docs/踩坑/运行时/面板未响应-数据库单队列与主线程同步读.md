# 面板「未响应」：数据库单队列 + 主线程同步读

> **何时阅读：** 改数据库访问层、面板数据刷新链路、或要给「主线程卡顿」加观测时。

## 现象

菜单面板出现「未响应」，活动监视器 CPU 99.4%，约 2 s 后自愈。生产日志零条，只能靠 `sample` 反推。

## 根因链条（实测）

1. 打开面板 → `refreshAll()` → `refreshToken()` → 后台 `runIndexing()`（扫描解析 DSH 会话 zstd 并写库）
2. 收尾 `publishSnapshot()` 在**唯一的数据库串行队列**上跑 8~10 条全表聚合（`harness_token_event` 16.9 万行，单次 0.2–1.0 s）
3. 同一条队列也服务主线程的 `serialQueue.sync`（剪贴板读取、面板打开路径）
4. 主线程排在聚合后面拿不到队列 → 2 s 内不处理事件 → 系统判「未响应」

实测：debug 版停 Token 页 5 s，CPU 时间 +2.4 s（≈半个核×5 s 平均，峰值单核 100%）；采样里 `database` 线程 587/1178 停在 `harnessAggregate` → `harnessWindowedUsage`。

## 修复要点

- **读写分队列**：`DatabaseManager` 增只读队列 + 只读连接（`sqlite3_open_v2` + `SQLITE_OPEN_READONLY`）。WAL 下只读连接**立即**读到写连接已提交的内容（实测同一毫秒内可见，不依赖 checkpoint）。只读接口（聚合 / 剪贴板 / 检索 / 扫描记录）走只读队列，写入与索引走写队列。
- **主线程同步读改异步**：剪贴板与 Token 快照的取用在后台队列，回主线程用「请求序号 + 只接受最新一次结果」（`LatestRequestGate`）渲染，慢的旧结果不会覆盖新数据。
- **聚合降频**：索引过程中不做全表聚合；只在（a）一轮索引结束、或（b）有未计入快照的写入时按需补算。无变更的重复刷新（开面板 / 切页）走内存缓存，零查询。
- **观测**：主线程看门狗（后台 0.5 s）+ 数据库队列排队等待计时（> 200 ms）+ 聚合耗时（> 100 ms）。事故现场没日志这件事比事故本身更贵。

## 踩过的坑

- **`:memory:` 库没有第二个连接**：内存库是每连接私有的，只读查询必须退化为走写队列（用 `isUsingDedicatedReadConnection` 自证），否则测试里读到空表。
- **只读连接不能建表**：`CREATE TABLE IF NOT EXISTS` 在 READONLY 连接上遇到「表不存在」会直接报 readonly。schema 迁移因此上移到 `migrateIfNeeded()`（启动时在写连接上建好），否则首次索引前的聚合会查空。
- **看门狗只靠业务定时器打点会假停顿**：面板在省电档是 2 s 一跳，阈值恰好 2 s → 每跳一条假日志。心跳必须再加一路「看护线程投到主线程的心跳块」（主线程活着就会执行，卡住就排队），判据才与业务节拍解耦。
- **`LogRedaction.path` 只看前缀**：日志正文里路径常夹在句中（「索引失败：未找到目录 /Users/x/…」），用 `paths(in:)` 做全位置替换。
