# NSPopover 面板展开时「先居中再跳到右边」

> 症状：点菜单栏图标展开面板，面板先在偏中间的位置停一瞬，然后「啪」地跳到右边贴着菜单栏图标。

## 现场

逐帧轨迹（`NM_PANEL_PIN_TRACE=1`，60Hz 采样，Cocoa 坐标原点左下）：

```
TRACE attach t=0   x=955.0 y=529.0 w=346.0 h=425.0
…
TRACE attach t=242 x=955.0 y=529.0 w=346.0 h=425.0   ← 前 14 帧停在 955
TRACE attach t=260 x=783.0 y=524.0 w=346.0 h=425.0   ← 第 15 帧才跳到 783
```

面板宽 346、状态项右边缘 1129（当时口径是右对齐），目标 x = 1129 − 346 = **783**。
popover 自己摆在了 **955** —— 这是它按锚点中心算出的落点（加屏幕夹取后）。

> 现行口径是「以状态项中心居中」（见 [面板顶端三角只在窗口中心](面板顶端三角只在窗口中心.md)），
> 目标 x 改为 `状态项中心 − 面板宽度/2`；本文讲的「横向纠正不能等动画结束」这条与口径无关，仍然成立。

## 成因

横向纠正逻辑（`PanelWindowPin`）与纵向共用同一道闸门：**「出场动画结束后（0.25s）才允许改窗口」**。

这道闸门是纵向必须的（动画期间窗口位置与尺寸都在变，插进去会和 popover 抢，
实测按动画帧取到的顶边比稳定值低 50pt），但它对横向是多余的：

- 横向锚点（状态项右边缘）在 show 时就已冻结；
- 出场动画期间 popover **不改横向位置**（上面前 14 帧全 955 就是证据）。

于是前 242ms 用户看到的是 popover 自己摆的居中位置，闸门一开就被纠正到 783 —— 一帧内的位移可见。

## 做法

把「能不能改」拆成两个维度，别再共用一个开关：

| 维度 | 何时可纠正 | 依据 |
|---|---|---|
| 横向 | show 之后**立刻** | 右边缘 show 时就冻结，动画不改横向位置 |
| 纵向 | 出场动画结束后 | 动画期间取不到稳定顶边（实测低 50pt） |

落点：

- `PanelAnchor.pinTarget(panelFrame:statusItemMaxX:lockedTopEdge:visible:)` 是纯逻辑：
  纵向没锁顶边时返回 `y == nil`，调用方据此只改 x、保持 y 不动；
- `PanelWindowPin.attach` 里在挂完观察者之后**同步** `pin()` 一次（此刻 `targetTopEdge` 还是 nil，只动横向）；
- 观察者回调在 armed 后**同步**纠正，仍再排一次补钉兜底 —— 同一次 resize 里 popover 可能分两步改 frame，
  同步改完这一步仍会被后一步覆盖。

## 复跑

```bash
cd NetworkMonitor && SKIP_INSTALL=1 ./Scripts/build-app.sh
osascript -e 'quit app "一览"'; sleep 2
(NM_PANEL_PIN_TRACE=1 dist/一览.app/Contents/MacOS/一览 > /tmp/trace.log 2>&1 &)
sleep 14
grep 'TRACE attach' /tmp/trace.log | sed -E 's/.*x=([0-9.]+).*/x=\1/' | uniq -c
```

判据：**整段只有一个 x 值**（改前是两个：14 帧 955 然后 783）。

## 顺带修掉的一帧中间态

同一份轨迹在切页后也抓到过一次漏帧：

```
TRACE switch t=0   x=945.0 …   ← 切到额度页的第一帧
TRACE switch t=17  x=783.0 …
TRACE switch t=857 x=954.0 …   ← 又漏了一帧
```

成因相同：popover 改 `contentSize` 会把自己按锚点中心重摆，而纠正排在下一轮 runloop。
把观察者回调里的纠正改成**同步**（armed 后）之后，这一段也归零。
