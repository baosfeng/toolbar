# 忽略鼠标事件的浮层自己收不到滚轮

> **何时阅读：** 准备做一个「悬停提示 / 只读预览」类浮层，既要求它不拦鼠标点击，又要求超长内容能在浮层内部滚动；
> 或者发现浮层弹出后滚轮完全没反应、事件被底下的列表吃掉。

## 历史问题：已随浮层删除而消失

这条问题的现场（剪贴板卡片的悬停全文浮层）已经不存在：完整内容现在常驻在面板底部的详情区里（见[剪贴板底部详情区](../../设计/剪贴板底部详情区.md)），
详情区是面板内的普通 `NSView`，滚动由它自己的 `NSScrollView` 正常处理，没有任何「收不到鼠标事件的窗口」。
记录保留下来，因为「`ignoresMouseEvents` 与内部滚动天然互斥」这条成因，对任何浮层类交互仍然成立。

## 成因

一个**不拦鼠标**的浮层通常会把窗口设成 `ignoresMouseEvents = true`，它同时是两条硬性要求的来源：

1. 浮层不能拦鼠标——用户还要能点卡片、点右键菜单，浮层只是「看一眼」的提示；
2. 正文超过可视高度时要在浮层内部滚动（`NSScrollView`）。

这两条直接冲突：`ignoresMouseEvents = true` 的窗口收不到任何鼠标事件，`NSScrollView` 的滚动条与滚轮处理全在事件链路里，
于是「滚动」这条需求天然落空——浮层里能看到滚动条，却拖不动、滚不动。

## 绕法（浮层方案仍然适用）

**滚轮由父视图转发，浮层只暴露一个纯函数入口。**

- 浮层提供 `scroll(by deltaY:) -> Bool`：只有浮层可见、内容确实超长时才消费这次滚动，自己改 `clipView.bounds.origin` 并 `reflectScrolledClipView`，返回 `true` 表示「已消费」；
- 宿主视图在 `scrollWheel(with:)` 里先问浮层，消费掉就 `return`，否则走 `super` 交回列表：

```swift
override func scrollWheel(with event: NSEvent) {
    if overlay.scroll(by: event.scrollingDeltaY) { return }
    super.scrollWheel(with: event)
}
```

- 判定「消费与否」必须是浮层的返回值，不能在外面按「浮层可见」猜：可见但内容不超长时仍要让滚轮落回列表，
  否则列表在浮层展开期间会莫名滚不动。

**更省事的做法**：把内容放进面板自身的一块常驻区域，让滚动留在普通视图树里，就不必再应付这条约束——这也是现在采用的方案。

## 如何识别

- 浮层里能看到滚动条、滚轮却没反应 → 先查浮层窗口是不是 `ignoresMouseEvents = true`；
- 浮层展开时列表也滚不动 → 查转发函数的「是否消费」判断是不是写成了「浮层可见即消费」；
- 浮层用 `.nonactivatingPanel` 且没收键盘事件时同理：键盘处理要走面板的本地事件监听转发，别指望浮层自己拿到 `keyDown`。
